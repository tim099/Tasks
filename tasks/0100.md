## 五、酒保／Discord：怎麼拆、為什麼是這個順序

### ⭐ 先講那個結構缺口 —— 它決定了全部順序

Server 的主迴圈是 `while (true) { Tick(); Thread.Sleep(500); }`，
而 `ServerExecutor.Tick()` **只掃 `queues/*/pending.trigger`** ⇒ **Server 今天是純請求驅動的**。

三隻 daemon 全是 `[InitializeOnLoad]` ＋ `EditorApplication.update` ⇒ **時間驅動**。

📌 ⇒ **搬 daemon 不是移植，是先要有一個新的宿主能力**（常駐排程層）。
⛔ 這一格不做，底下 B／C／D 三條都搬不動 —— 而它們的 daemon 迴圈**沒有人在對面接**。

### 拆法：按**宿主需求**切，⛔ 不按檔案目錄切

| # | 子系統 | 行數 | 宿主需要什麼 | 難度 |
|---|---|---:|---|---|
| **A** | **常駐排程層**（Server 的 `every N sec` 那一格） | 新寫 | — | 前置，其餘三條的共同前提 |
| **B** | Discord **Outbound**（Mirror／Webhook／TreasuryMirror／MirrorState） | **2430** | 排程 ＋ HTTP | 低：單向送出、無長連線、失敗可重試 |
| **C** | Discord **Inbound**（InboundDaemon ＋ GatewayClient） | **1507** | 排程 ＋ **WebSocket 長連線** | 中 |
| **—** | `UCL_DiscordIdentityResolver` | 243 | — | B、C **共用**，跟著先搬的那一條走 |
| **D** | **酒保**（Bartender） | **7681** | 排程 ＋ LLM ＋ **Windows 視窗自動化** | 高，且它自己要再拆兩段 |

**D 自己的兩段**（⛔ 不要當成一件事）：
- D1 判斷與發言：`Cmd_Bartender`／`BartenderDaemon`／`IO`／`InlineParser`／`Models`／
  `MentionService`／`CliService`／`CliCommandConfig`／`CliSettings`／`LLMSettings` ＝ **4627 行**
- D2 遠端戳窗：`RemoteNotifyService`／`RemoteWindowControl`／`RemotePersonaLocator`／
  `RemoteAgentInput` ＝ **3054 行** —— ⚠ 這是整條線裡**唯一會替使用者按 Enter** 的流程。

### ⭐ C 搬過去會**順便修掉一個既有缺陷**（讀數在它自己的檔頭）

`UCL_DiscordInboundDaemon` 檔頭逐字寫著 REST 安全網存在的第一個理由：
「① **Editor domain reload 頻繁會砍長連線**；輪詢無狀態…」
⇒ Server **沒有 domain reload** ⇒ 搬過去之後那條安全網的**成因消失**。
⛔ 但不要順手把安全網拆掉 —— 它還擋著 gateway INVALID_SESSION 那一族，那是另一件事。

### 舊的建議順序（2026-09-21 上午）：`0263 → 0106 → A → B → C → D1 → D2`
> ⚠ **下面 §六 有 Tim 的拍板，B/C 的落點與理由都變了 —— 以 §六 為準。**

1. **0263 先**（它 `blocks 106`）：病是「委派靜默遺失而 client 一律 exit 0」。
   ⛔ 不准在一個**會安靜掉工作**的宿主上疊新負載 —— 那會讓 B/C/D 的每一個失敗都長得像沒發生。
2. **0106 次之**：酒保／Discord 三條**全部依賴酒館寫入**（酒保發言、inbound 落訊息、outbound 讀訊息）。
   先讓寫入端定下來，後面三條就只需要改**宿主**，不必同時改**寫入路徑**。
3. **A 前置**：沒有它，B/C/D 搬過去沒有人 tick。
4. **B 先於 C**：outbound 單向、無狀態、失敗可重試 ⇒ 它是排程層的第一個真實負載。
   ⭐ **用 B 驗 A 比用 C 驗便宜**：B 壞掉只是訊息晚到，C 壞掉是**漏收**。
5. **D 最後**：面積最大、依賴最多，而且**它依賴 B/C 還活著**（酒保的通知走 Discord）。
   D2 再往後 —— 它會替人按 Enter，錯了的代價不在資料上。

### ⛔ 這份路線圖裡我**沒有量**的（寫出來，不藏）

- 三隻 daemon 搬過去對 Server lane 排程的實際成本（CPU／IO）—— **一格沒量**。
- `UCL_RemoteWindowControl` 在 Server 那顆 process 底下拿不拿得到同一個桌面 session —— **沒試過**。
- 酒保的 LLM 呼叫在 .NET 那側有沒有現成客戶端可用 —— **沒查**。
- 上面所有行數都是 `wc -l`（含註解與空行）⇒ 它量的是**面積**，⛔ 不是工作量。

## 六、Tim 2026-09-21 下午拍板：**Discord 自己一顆，Inbound＋Outbound 都在裡面**

### 拍板同時給了兩個以前沒寫下來的前提

1. **延遲 1 秒可接受** ⇒ 效能整條軸拿掉。
2. **切 Server 還有第二個目的：可以同步動工**（同 sln 不同 project）——
   ⛔ 這一格以前只當成「執行期故障隔離」，而它其實也是**開發期**的隔離。

### 🔬 而「同步動工」的現況：編譯層已成立，**運行層還沒有**

- sln 裡已經有 **5 個 csproj**：`SCP_Core` / `Senate.Core` / `Senate.Cli` / `Senate.Server` / `Senate.Desktop`。
- `Senate.Server` 早就是**獨立 exe**（`AssemblyName = senate-server`，只 ProjectReference `Senate.Core`，
  且檔頭明令 ⛔ 不准引用 `Senate.Desktop`）——TASK-0209 那四格之一。
- `build.sh` 是**兩次 publish、兩顆 exe**：`publish/senate.exe`（:128）與 `publish/server/senate-server.exe`（:145）。

⇒ 📌 **真正卡住同步動工的不是專案切分，是 `build.sh:66` 的 `server stop --all`** ——
任何人 build，**每一顆** Server 都會停。
🩸 活體血證（2026-09-21 15:10~15:14，basecamp）：@kotoko 在施工場裡跑 build（`publish/senate.exe`
重建於 15:14:11），我兩次 `senate server start`（15:10 / 15:12:45）都被停掉，
而**反方向的傷害是我造成的** —— Server 活著會鎖住 `publish/senate.exe`，她的 publish 可能撞 Access denied。
⇒ ⚠ 那個 `--all` 是**刻意**的（腳本註解：漏停一顆的樣子是 publish 撞鎖）。
　 要同步動工就得讓它**只停自己要覆寫的那顆**，而前提是每顆 Server 有**自己的 exe 與 publish 目錄**。

### 方案：`Senate.Discord` 自己一個 csproj / 自己一顆 exe / 自己一顆 Server

形狀照抄 `Senate.Server`：`OutputType=Exe`、`AssemblyName=senate-discord`、只引 `Senate.Core`、
publish 到 `publish/discord/`。⇒ 改 Discord 不必碰 `senate.exe`，也不必停酒館那顆。

**Inbound 怎麼寫酒館**：走**現成的檔案協議委派**（⛔ 不引 broker、不自刻 socket）。

🔬 為什麼它夠用：`ServerExecutor.RunLane` 一次 `LoadQueue` 之後**跑完整批**
（`▶ lane 'x'：N 筆`）⇒ **500ms 是接手延遲，不是每筆上限**。
上限 10 筆/秒對它不構成壓力，而它的成本落在延遲 —— 那一軸 Tim 已經拍板不在乎。

⭐ **而讓它穩的關鍵不是傳輸，是游標什麼時候推進**：

> **酒館寫入確認成功，才推進 `last_message_id`。**

⇒ 失敗的樣子從「訊息**靜默消失**」變成「**積壓＋重試**」。
⚠ 重試必然重送 ⇒ 拿 **Discord 的 message id 當冪等鍵**（天生唯一，inbound 本來就在用它去重）。

### 🔴 前置：兩格，⛔ 不補的話 Inbound 放哪顆都會靜默出錯

| # | 補什麼 | 不補會怎樣 |
|---|---|---|
| **P1** | `ServerContext` 加一格「**我是哪一顆**」；`ServerDelegateCmd.Execute` 從 `if (InServer)` 改成 `if (InServer && 我就是目標那顆)` | 今天 `ServerContext` 只有 `InServer`(bool)/`Pid`/`BuildId`，**沒有 id** ⇒ 一支 `ServerId=tavern` 的 Cmd 在 Discord 那顆裡被呼叫會**就地執行**，安靜地變成第二個酒館寫入端（輸出一模一樣，只有 pid 不同）。⚠ 今天沒人踩到，因為只有 `main` 在服務 |
| **P2** | Discord 那顆的**常駐排程層**（原 §五 的 A） | daemon 是時間驅動，而 Server 的 `Tick()` 只掃 queue/trigger ⇒ 搬過去沒有人 tick |

📌 另有一格不是前置但同源：**`build.sh` 的停機射程**要從 `--all` 收窄成「只停我要覆寫的那顆」，
否則「同步動工」在運行層仍然不成立。

### ⛔ 評估過但不採用的（理由寫下來，免得日後重議）

- **Redis／NATS／Kafka**：多一個要運維的元件。成本落在每天，收益落在還沒發生的規模上。
- **自刻 loopback HTTP／named pipe**：低延遲不需要，而它要自己重寫超時／重試／錯誤報告／健康檢查
  —— 那四樣現成的檔案協議都有（exit code、`_cmd_errors/<id>.md`、result 檔）。
- **Inbound 併進 `tavern` 那顆**：協議最省（in-process 寫入），但把第三方長連線放進系統心跳那顆，
  且與「Discord 的東西在一起」相反。⚠ 它仍是 P1 出問題時的退路。

### 新的順序

`P1（Server 身分）→ P2（排程層）→ Outbound → Inbound → build.sh 停機射程收窄 → D1 酒保 → D2 戳窗`

- **P1 最先**：它是「多顆 Server」這件事**現在唯一會靜默出錯**的地方。
- **Outbound 先於 Inbound**：它純讀酒館、只寫自己的 cursor ⇒ **零跨 server 寫入**，
  是驗 P2 最便宜的第一個負載（⭐ 壞掉只是訊息晚到，Inbound 壞掉是**漏收**）。
- **build.sh 收窄排在 Inbound 之後**：在那之前 Discord 那顆本來就會被別人的 build 停掉，
  而那時它還沒承擔不可漏的工作。
- **D1/D2 最後**：面積最大、依賴最多，且酒保的通知走 Discord ⇒ 它依賴 B/C 已經穩。

### ⛔ 這一節我沒量的

- Discord inbound 的**實際**流量 —— 10 筆/秒是 Tim 給的**上限**，不是量出來的值。
- 批次寫入時酒館 seq 配號的行為（一次派 N 筆 vs 派 N 次一筆，哪個對）—— 沒讀。
- daemon 搬過去對 lane 排程的成本 —— **連續第三輪未量**，這裡標第三次。

**編輯介面不必新造** —— `SCP_Core/Runtime/Gui/` 已有整套頁框架（15 檔 2936 行：

Senate.Cli 底下已有 9 頁在用它（`BankAdminPage` 1620 行是最大的那個樣板）。
⭐ 而它**同一份頁面碼兩個 renderer**：`senate ui --window` 給人看，
`senate ui --list / --set / --click` 給沒有眼睛的人改 ⇒ **agent 不開 GUI 也編得動設定**。

**`SCP_Prefs` 就是 EditorPrefs 的替代品，而且它是刻意不抄 PlayerPrefs 語意的**（檔頭逐字）：
① key 打錯回預設值 ⇒「打錯」與「沒設定過」同形；② 型別靠呼叫端記得；③ 沒有「未設定」態。
⇒ 它的 scalar 讀取回**三態**，「讀不到就用預設」必須顯式呼叫 ⇒ 正好擋住
