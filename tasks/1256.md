## 任務描述

## 為什麼

TASK-1252 放寬自動建築（一輪不設上限）之後，起始檔＋發船一年的模擬從 370 秒變成 726～820 秒（同一批量的；建築多了八成）。之後還要加很多城，每天的模擬要省下來。

## Tim 原話（2026-11-07，summit 的 session）

- 「計算模擬是否能優化 因為之後還會新增很多城市 可以分析一下哪些部分能簡化(只要宏觀模擬結果接近即可 且在玩家不會注意到的部分可以簡化模擬)」
- 「例如同種建築合併計算?(特別是混合配方的)」
- 「然後判斷切換配方的頻率可以降低 以及看目前性能瓶頸」
- 「然後算法希望不要太複雜化(考慮到效能&可維護性)」（講需求算法時說的，同一個原則）
- 「1252 照不設上限，效能另開單」

## 剖析讀數（summit，TASK-1252 分支，起始檔＋發船 180 天、期末 14,652 棟；每一步包住計時＋ node --cpu-prof）

| 步驟 | 佔每天的 | 裡面最重的 |
|---|---|---|
| 自動建築 autoDay | 42% | 每挑一座都重建候選清單 candidates（11%）；週轉金 reserve ⇒ upkeep 每個候選掃全世界的建築再算 prodFull（8.5%）；服務建築候選 svcCandidates（7%） |
| 生產 prodDay | 19% | 每一棟每天 prodFull／plan（12%）；famSellDay（6%） |
| 吃飯 townEat | 18% | 每座城每一層各算一次 dishes（5%） |
| 船隊 fleetDay | 12% | routeEval／evalDest 重估航線（8%） |
| 服務建築 serveDay | 3% | |
| 換配方 recipeDay | 2.4% | |
| 區域需求表 regionTable | 1.9% | |

另外：marketIsFood 每次查價都重算、還掃一遍 SHIP_RECIPES（shipProv）—— 6.4%；GC 7.6%。

## 三層（summit 的建議：先做第一層）

1. **純快取，結果逐位元組不變**：marketIsFood 記起來；upkeep 每輪每個主人只算一次；一輪連挑時候選清單只建一次；菜單一天一城算一次各層共用。推估省 25～35%。upkeep 那一段是「候選 × 全世界建築」，城越多越吃。
2. **同種建築合併計算**（Tim 提的）：同城、同種、同級、同配方、同主人合成一組算一次（混合配方的料也只挑一次）；工人數再拆回每一塊地給遊戲畫面。改動較大、結果可能有很小的差。
3. **降低頻率**：換配方只佔 2.4%（照 Tim 說的可以降，但不是瓶頸）；船隊航線只在到港或需求變了才重估。

⚠ 計時有雜訊：同一份程式量過 452 秒和 589 秒（筆電溫度、背景負載）—— 比較要同一批、配雙胞胎。
