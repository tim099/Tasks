# TASK-0162 — 逐支把卡住主執行緒的 Cmd handler 移出主緒（依 TASK-0161 的讀數排序，不打包）

> `improvement` / `high` / `in_progress`　開單：summit　參與：summit(dev)

## 驗收標準

① 有一個**共用的 offload helper**（prewarm 主緒 only 的路徑快取 → RunOnThreadPool → SwitchToMainThread），逐支改的 handler 走它，不要 40 份各自重造。
② **逐支交付、逐支拿讀數**：每改一支，用 TASK-0161 的量具對拍——改前 `kind=stall` 有斷拍歸因到它、改後同一支同樣負載**不再出現在斷拍的 overlapping_cmds 裡**，而 `elapsed_ms` 仍然大（證明工作沒變少，只是換了執行緒）。
③ ⛔ **不打包**：一次 commit 一支（或一族），每支在單上留讀數。哪一支不能 offload 也要寫明理由。
④ ⛔ `Cmd_Task` 族**不在本單射程**：`UCL_TaskIO.cs:202` 的 `AssertMainThread` 明寫該檔沒有鎖、併發安全依賴「單一主執行緒 ＋ RMW 中間沒有 await」。要動它得先給資料層上鎖 ⇒ 另開單。
⑤ 每支改完要跑 `senate cmd unity-recompile` 拿 clean，且**不改任何 cmd 的對外行為**（回傳檔內容、result 檔、公告都不變）。

48 支 handler 只有 1 支真的閃開主執行緒（`Cmd_GoodMorning` step=brief）。

## 為什麼不能一律 offload（這格是本單的核心約束）

- `UCL_TaskIO.cs:202` `AssertMainThread`：該檔**沒有鎖**，併發安全**完全依賴**「單一主執行緒 ＋ RMW 中間沒有 await」。
- 路徑解析層碰主緒 only 的 API（`UCL_AgentCommandsPath.DataRoot` → PlayerPrefs、`UCL_RepoPath` → `Application.dataPath`）⇒ 背景緒直接呼叫會丟例外，而**它的失效樣子是 cmd 失敗一次**（比靜默好，但仍要先 prewarm）。
- Runner 的 catch 用 `EditorApplication.isPlayingOrWillChangePlaymode`（主緒 only）⇒ **不在 Runner 那一層切執行緒**，切在 handler 內（已有四個先例：GoodMorning brief / KnowledgeBase / MediaAdmin / LLMAdmin runner）。
