## 需求原文（Tim）
> 獲取觀影片段觀看後，訊息再透過目前分配片段的系統發送，確保片段 1,2,3,4 訊息發送順序會維持 1,2,3,4
> （即使先發了 2 的訊息，也會等 1 發出時才一次發出 1,2 的訊息 —— 訊息不會立刻發出，而是有一定延遲確保不會亂序，
> 但可能要有 Timeout（預設 60 秒，後台可調））。Timeout 算法：假如後面的訊息先到（例如 2 號到了、在等 1 號），
> 從 2 號收到當下開始倒數，超時後視為 1 號片段失效（自動標記為熱點片段補看）。

## 設計（含 Tim 後續兩次拍板修正）
- `observe` 不直發 → 寫 `StreamWatch/observe_queue.jsonl`（append-only，含 seg_index／body 檔路徑／enqueued_at／deadline）
- flush 條件：同一 relay_key 上所有更小的 seg_index 都已 posted 或已放行；同段多則按 enqueue FIFO
- **入列即計酬，且入列的一定會發送**（Tim 拍板）⇒ 不是三段帳，是「入列＝承諾必發」＋「發文只是延遲」
- **觀影中斷或結束時直接 flush queue**（Tim 拍板）⇒ 「最後一段卡在佇列」的失敗模式消失
- Timeout 預設 60s、後台可調（沿用 `_screenstream/_config.json` 慣例）；
  **deadline 用絕對時戳不用倒數器** —— Tim 說觀影期間不會 compile，但這個前提不該被寫死進機制
- 逾時 ⇒ (a) 放行後面的、(b) **把缺的那段標熱點**（複用 `hotspots.json`，why 自動填「接力段 #K 逾時未交」）
  ⚠ 逾時**不作廢**（因為入列必發）：遲到那則照發並標 `late=true`，熱點是「補看邀請」不是「作廢紀錄」

\## Tim 2026-08-26 追加設計輸入：仿 `UCL_ProcessRegistryService` 做中斷續接

> 「假如真的擔心觀影中途 Editor 出問題（也不一定是 compile），可以參考 UCL_ProcessRegistryService 的概念，

> 每次重啟時清除暫存檔案資訊（且不進入 git）。」

\## ⚠ 這裡有一個必須先解開的衝突：**「重啟清除」與「入列必發」不能同時成立**

佇列裡的每一則觀察都**已經計酬**（Tim 拍板：入列即計算、入列的一定會發送）。
⇒ 若照「重啟就清暫存」處理，一次 Editor 崩潰會**靜默銷毀已付錢的觀察** ——
帳上有 observations，河道上沒有那一則，而**兩邊都不會喊**。這正是「帳與產物脫鉤且不報錯」那一族。

⇒ 所以要**按生命週期分成兩類**，不能一視同仁：

| 類別 | 內容 | 重啟時 | 進 git？ |
|---|---|---|---|
| **liveness / 執行中狀態** | 本場 in-flight（正在等水位、montage 跑到哪） | **可清**（驗證過死亡才清） | ❌ |
| **pending 承諾** | `observe_queue.jsonl`（已計酬未發文） | **絕不可清** → 開場／重啟時**先 flush** | ❌（但要活過重啟） |
| **durable 台帳** | `sessions_log.jsonl`、**`segments.jsonl`**（TASK-0060） | 永不刪 | ✅ 要進 |

📌 第三列很重要：**段台帳不能當暫存**。TASK-0061 的書要靠 `seg_index → seq` 排序，
而書可能在**幾週後**才重出（010.txt 的備註就寫著要重出）⇒ 對照表必須跟書一樣長壽。
⇒ Tim 的「不進 git」適用於前兩列，**不適用於段台帳**（它跟 `sessions_log.jsonl` 同一級）。

\## 照 ProcessRegistry 抄什麼、不抄什麼

**抄**：
- **每場一檔**（`<tag>_<id>.json`）而不是集中一檔 —— 避免併發互蓋、單檔壞不連坐
- 落在主專案 `AgentCommands/` 底下（runtime 狀態、per-project、不入 UCL_Core repo）
- 清理掛 `InitializeOnLoad` 跑一次（現成的自動觸發點，fire-and-forget 沒有 finally 可用）

**不能抄**：`CleanupStale()` 的**死亡判定**。
它靠 `pid + process_name + start_time_utc` 三重比對（PID 會被 OS 回收再發，光 PID 會誤殺），
而**觀影 session 背後沒有 process** —— agent 是 LLM session，沒有 pid 可驗。
⇒ 要另找可驗的死亡證明，而現成的就是 cycle 收工判定已經在用的那兩個顯式狀態：
① `end_ts` 已過（到期）② `_screenstream/_config.json` 的 `enabled=false`（Tim 停錄影 —— Tim 說得對，錄影狀態本來就是寫檔的）
⚠ **不要用 frame 新鮮度推論**（現行 cycle 的註解就明寫「本判定只認顯式狀態，不推論 frame 新鮮度」）。

⇒ sweep 規則：**session 到期或錄影已停 ⇒ 該場 scratch 可清；但清之前必須先 flush 它的 queue**。
順序反了就是「清掉之後才發現裡面還有沒發的東西」，而那時已經沒有東西可發。

\## 另一格：`CleanupStale` 是**驗證過才刪**，不是重啟全清
這是我讀 code 後要更正的一格 —— Tim 說的「每次重啟時清除」若照字面實作成 blanket wipe，
就會失去 registry 最值錢的性質：**它能在 domain reload 後「接管」還活著的 process**（檔案留著才接得回）。
⇒ 對觀影而言等價的收穫是：**重啟後還在時限內的場次應該能續接**，而不是被清掉重開。
