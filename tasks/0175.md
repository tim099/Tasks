## 任務描述

## 症狀

**裸 `Tavern op=read` 一律失敗**，而帶 `--arg tail=` 或 `--arg limit=` 就成功。

```
$ senate ucmd run Tavern --persona summit --arg op=read --arg room=tavern
  ✗ Cmd failed: 執行 op=read 失敗：HasKey can only be called from the main thread.
    at UnityEngine.PlayerPrefs.HasKey (System.String key)
    at UCL_ChatTavernSettings.Get (…) UCL_ChatTavernSettings.cs:177
    at UCL_ChatTavernSettings.get_ReadTailCount () UCL_ChatTavernSettings.cs:59
    at Cmd_Tavern.Op_Read (…) Cmd_Tavern.cs:1733
  📄 D:/Unity/LY/AgentCommands/_cmd_errors/20260908-085022-251412-tavern.md
```

## 成因（讀出來的，不是推的）

`Cmd_Tavern.cs:241` —— `op=read` 已經 offload 到背景緒（TASK-0162 的既有交付）：

```csharp
case "read": await UCL_AgentCmdOffload.EnterBackground(args); Op_Read(args); break;
```

而 `Op_Read` 會讀 `UCL_ChatTavernSettings.*`，那個類別走 **`PlayerPrefs`**（`UCL_ChatTavernSettings.cs:177`
的 `PlayerPrefs.HasKey`）—— **`PlayerPrefs` 是主緒限定的 Unity API**，在背景緒上呼叫直接丟
`InvalidOperationException`。

## ⭐ 為什麼三週沒有人撞到：壞的是**預設路徑**，而它躲在三元短路後面

`Op_Read` 裡三處 settings 呼叫**全部**寫成「參數沒給才求值」：

| 落點 | 程式碼 | 什麼時候求值 ⇒ 什麼時候炸 |
|---|---|---|
| `Cmd_Tavern.cs:1733` | `int n = tail > 0 ? tail : (limit > 0 ? limit : UCL_ChatTavernSettings.ReadTailCount);` | `tail` 與 `limit` **都沒給** |
| `Cmd_Tavern.cs:1710` | `Search(roomId, search, limit > 0 ? limit : UCL_ChatTavernSettings.SearchLimit)` | 給了 `search`、**沒給 `limit`** |
| `Cmd_Tavern.cs:1715` | `Since(roomId, since, limit > 0 ? limit : UCL_ChatTavernSettings.SinceLimit)` | 給了 `since`、**沒給 `limit`** |

⇒ C# 三元**短路** ⇒ 只要呼叫端帶了那個參數，`PlayerPrefs` 那一行**根本不會被執行**。
⇒ **習慣帶 `tail=` 的人永遠不會遇到；第一次用、照文件打 `op=read` 的人一定遇到。**
📌 一般形：**offload 之後的主緒違規，如果藏在「預設值」的求值路徑上，
它的觸發條件是「呼叫端少給一個參數」——而那正好是最沒經驗的那次呼叫。**

## 🔬 對照組（變因單一，每組只差一個參數）

| # | 指令 | 結果 | stack 裡的 getter |
|---|---|---|---|
| A | `op=read --arg room=tavern` | **✗ 失敗** | `get_ReadTailCount` |
| B | `op=read --arg room=tavern --arg tail=3` | ✓ Success | —— |
| A′ | 重跑 A（確認不是偶發） | **✗ 失敗**（同一條 stack） | `get_ReadTailCount` |
| C | `op=read --arg room=tavern --arg search=像素` | **✗ 失敗** | **`get_SearchLimit`** |
| D | `op=read --arg room=tavern --arg search=像素 --arg limit=3` | ✓ Success | —— |

⇒ A/B 與 C/D 兩組各自只差一個參數 ⇒ 成因不是「op=read 壞了」，
是**那三個預設值的求值位置在背景緒上**。

## ✅ 射程（我量到哪裡）

- **量到 2 條**：`ReadTailCount`（A/A′）與 `SearchLimit`（C）。
- ⛔ **`SinceLimit` 那條我沒跑** —— 程式碼結構與另兩條逐字同形，但那是推論不是讀數。**標未量。**
- **`op=catchup` 也 offload（`Cmd_Tavern.cs:267`）但它一格 settings 都沒碰** ⇒ 不受影響。
  活體：今天 08:32 的 `morning-catchup` 正常跑完（unread=54、游標推進）。
- ⛔ 我**沒有**掃過其他已 offload 的 handler（`AutoCommit` 全支）有沒有同族的主緒 API。
- `Cmd_Tavern.cs:493` / `:1015` 也讀 `LastViewTailCount`，**那兩處屬哪個 op 我沒查** ⇒ 未量。

## 修法建議（不打包，交 PM／dev 判）

**⛔ 不是「叫大家記得帶 tail」** —— 那是把 bug 寫進使用慣例。

- **(甲) `EnterBackground` 之前先把 settings 快照成區域變數**（每個 offload 過的 op 各自負責）。
  ⚠ 代價：新增 offload 時要記得做 ⇒ **會漂**，而漂掉的症狀就是這張單。
- **(乙) `UCL_ChatTavernSettings` 自己在主緒快取**（`InitializeOnLoadMethod` 預熱 ＋ 之後純讀記憶體）。
  ⭐ 一處修完全部，而且它讓「settings 是主緒限定的」這個事實**不再是每個呼叫端要記住的東西**。
  📌 這個方向與 TASK-0163 我剛拿到的判準同形：**跨度由型別／機制決定，不由每個呼叫端記得。**
- **(丙) `UCL_AgentCmdOffload` 加一道守衛**：offload 的 handler 碰主緒 API 時給一句人看得懂的話
  （現在的訊息是 Unity 原生的「移到 Awake 或 Start」——**對 Cmd 作者完全沒有指向性**）。

⚠ 甲乙丙不互斥；(乙)＋(丙) 我認為最省，但**這是判斷不是讀數**，dev 可以退回。

## 為什麼值一張單而不是併進 TASK-0162

0162 是「逐支把卡住主執行緒的 handler 移出主緒」——**它是動作**。
本單是那個動作**已落地的一支留下的回歸**，而且它揭露一個 0162 缺的東西：
**offload 之前沒有人在問「這支 handler 碰不碰主緒限定 API」。**
⇒ 本單修完應該回頭給 0162 加一格驗收（offload 一支之前先掃它的 Unity API 面），
但那一格要不要加是 0162 的事，我不替它改條文。

## 📌 severity 我填 `wrong` 不填 `blocking`，理由寫在這裡讓人能上調

裸 `op=read` 是**硬失敗**（例外、零輸出），照字面比 `wrong` 重。
但我自己一分鐘就繞過去了（帶 `tail=`）⇒ 宣告 `blocking` 是一個**我沒量過的影響**
（沒有人因為它停下來過，至少我沒有讀數）。
⇒ 誰量到有人真的卡住（例如新人照文件打、拿不到訊息就放棄），**請直接上調**。
