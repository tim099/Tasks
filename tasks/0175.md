## 症狀

**裸 `Tavern op=read` 一律失敗**，而帶 `--arg tail=` 或 `--arg limit=` 就成功。

```
$ senate ucmd run Tavern --persona summit --arg op=read --arg room=tavern
  ✗ Cmd failed: 執行 op=read 失敗：HasKey can only be called from the main thread.
    at UnityEngine.PlayerPrefs.HasKey (System.String key)
    at UCL_ChatTavernSettings.Get (…) UCL_ChatTavernSettings.cs:177
    at UCL_ChatTavernSettings.get_ReadTailCount () UCL_ChatTavernSettings.cs:59
    at Cmd_Tavern.Op_Read (…) Cmd_Tavern.cs:1733
  📄 D:/Unity/LY/AgentCommands/_cmd_errors/20260908-085022-251412-tavern.md
```

## 成因（讀出來的，不是推的）

`Cmd_Tavern.cs:241` —— `op=read` 已經 offload 到背景緒（TASK-0162 的既有交付）：

```csharp
case "read": await UCL_AgentCmdOffload.EnterBackground(args); Op_Read(args); break;
```

而 `Op_Read` 會讀 `UCL_ChatTavernSettings.*`，那個類別走 **`PlayerPrefs`**（`UCL_ChatTavernSettings.cs:177`
的 `PlayerPrefs.HasKey`）—— **`PlayerPrefs` 是主緒限定的 Unity API**，在背景緒上呼叫直接丟
`InvalidOperationException`。

## ⭐ 為什麼三週沒有人撞到：壞的是**預設路徑**，而它躲在三元短路後面

`Op_Read` 裡三處 settings 呼叫**全部**寫成「參數沒給才求值」：

| 落點 | 程式碼 | 什麼時候求值 ⇒ 什麼時候炸 |
|---|---|---|
| `Cmd_Tavern.cs:1733` | `int n = tail > 0 ? tail : (limit > 0 ? limit : UCL_ChatTavernSettings.ReadTailCount);` | `tail` 與 `limit` **都沒給** |
| `Cmd_Tavern.cs:1710` | `Search(roomId, search, limit > 0 ? limit : UCL_ChatTavernSettings.SearchLimit)` | 給了 `search`、**沒給 `limit`** |
| `Cmd_Tavern.cs:1715` | `Since(roomId, since, limit > 0 ? limit : UCL_ChatTavernSettings.SinceLimit)` | 給了 `since`、**沒給 `limit`** |

⇒ C# 三元**短路** ⇒ 只要呼叫端帶了那個參數，`PlayerPrefs` 那一行**根本不會被執行**。
⇒ **習慣帶 `tail=` 的人永遠不會遇到；第一次用、照文件打 `op=read` 的人一定遇到。**
📌 一般形：**offload 之後的主緒違規，如果藏在「預設值」的求值路徑上，
它的觸發條件是「呼叫端少給一個參數」——而那正好是最沒經驗的那次呼叫。**
