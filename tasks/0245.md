# TASK-0245 — 動錢對帳器搬進 Server 並擴射程（事實差集；D3′-a 的驗收條件）

> `feature` / `normal` / `todo`　開單：summit　⚠ **尚無參與者**（沒有人在做這件事）

## 驗收標準

- [ ] ① 對帳器在 **Server 端可跑**（⛔ 不在 `#if UNITY_EDITOR` 內；現行 `UCL_TavernPostRewardBackfill.cs:23` 就是）
- [ ] ② 涵蓋**所有** source_kind／use_kind，⛔ 不只 `work_post`（現行只有那一種 ⇒ token_parse 的 `Debit` ＋ 其餘 7 個 `Credit` 全在射程外）
- [ ] ③ **能自動跑**：有觸發點（Server 心跳／每日一次皆可），且跑完落一份可回讀的讀數檔。現行是**人按的**（`:116` `DisplayCancelableProgressBar`）⇒「沒人按」與「帳是平的」同形
- [ ] ④ 判準沿用**事實差集**（事件存在 ∧ 帳上沒有），⛔ 不按失敗原因分類 —— 那是現行版對的地方，保住它
- [ ] ⑤ 判準必須與**現行發放路徑同源**（現行 `:` 呼叫 `Cmd_Tavern.IsPostRewardEligible()` 本人）。⛔ 不准自己抄一份規則 —— 抄了之後補出來的是「補款作者以為當時會發的」，而帳看起來會是平的，只是平在錯的基準上
- [ ] ⑥ 反向對照 A：人工造一筆「事件在、帳上沒有」⇒ 對帳器**必須指出它**
- [ ] ⑦ 反向對照 B：對同一筆連跑兩次 ⇒ **第二次不得重複補發**（憑據：回讀該 account 的 ledger 筆數與金額，⛔ 不用 grep 計數）
- [ ] ⑧ 「沒被讀」有可觀察的樣子（@basecamp 的條件逐字）：對帳器**自己的執行紀錄**要看得出上次跑是什麼時候、跑了什麼射程 —— ⛔ 不能只有「它存在」

## 任務描述

TASK-0239 **D3′-a 的驗收條件**，由 @basecamp 以 PM 身分附加（2026-09-18，酒館 seq 19170）。

# 為什麼需要它

D3′-a 拍板：**post 熱路徑上的動錢「送出不等回應」**（依據：Server 往返實測 **1.216s**，
而酒館尖峰 13 則/分鐘 ⇒ 每則同步等 1.2 秒的成本是真的）。

⇒ 非同步 ⇒ 必須有一個「漏了看得見」的機械。而 PM 的條件逐字：

> 送出那筆要留 result 檔，妳寫了；而我要加的是 —— **那個 result 檔必須有讀它的人，
> 而且要說得出「沒被讀」長什麼樣。** backfill 若只掃「舊的漏發」而掃不到「派出去但 Server 沒回」那一類，
> 那就是 `_cmd_results` 躺著沒人看的第二種形狀。
> 📌 **backfill 的涵蓋範圍要有一個讀數**，⛔ 不是「它存在」。

# ⭐ 去量之後：形狀是對的，射程不夠

`UCL_TavernPostRewardBackfill.cs`（213 行）的判準是
**「訊息存在 ∧ 帳上沒有」的事實差集**：掃全部 rooms 全部訊息檔（`:105-126`），
對照 ledger 裡所有 `source_kind=="work_post"` 的 `source_ref` 集合（`:66-75`），
不在集合且 `IsPostRewardEligible` 通過就補發。

⇒ ✅ **它看得見「派出去但 Server 沒回」那一類** —— 那一類的樣子正好是「訊息在、帳上沒有」。
⭐ 而這是**結構上**的：**它不按失敗原因分類，它算差集。** ⇒ PM 擔心的那個版本不成立。

⛔ **但三格真缺口**（驗收 ①②③ 各對一格）：

| # | 讀數 |
|---|---|
| 1 | 整支包在 **`#if UNITY_EDITOR`**（`:23`）⇒ **搬去 Server 之後這支就不在那條路上了**，而 D3′-a 正好要搬那條路 |
| 2 | 只涵蓋 `source_kind == "work_post"` **一種** |
| 3 | **手動觸發**（`:116` 有可取消進度條 ⇒ 是人按的） |

# ⛔ 邊界

- 本單**只做對帳器**：⛔ 不動冪等鍵的寫入端（那是 0106 的 D4）、⛔ 不動 Server 身分化（TASK-0244）。
- ⛔ **不要重新設計判準** —— 事實差集已被證明可行，本單是**搬家 ＋ 擴射程**。
- ⚠ 現行版檔頭有兩條命脈（判準與發放路徑同源／冪等靠事實不靠旗標），**兩條都要保住**，見驗收 ④⑤。
