### 🔬 證據（開單時附；含「讀數怎麼拿到的」）

**讀數（code 讀數，位址可複驗；⛔ 未取執行期重現）**

`Assets/Scripts/UI/HButton.cs`，`HButton.Init(HButtonSetting setting)`：

```csharp
var sprite = setting.icon.GetData().Sprite;   // ← GetData() 回 null 就炸在這一行
if (sprite != null) image.sprite = sprite;    // ← 這道判斷擋的是 Sprite 為 null，不是 GetData 為 null
```

`GetData()` 的失敗路徑是**明確回 null**，不是丟例外 ——
`Assets/Plugins/UCL_Core/UCL_Core_Scripts/AssetCore/UCL_Assets/UCL_AssetEntry.cs:62-74`：

```csharp
public T GetData(bool iUseCache = true)
{
    try { return Util.GetAsset(ID, iUseCache) as T; }
    catch (Exception e) { Debug.LogError(...); Debug.LogException(e); }
    return null;                                   // ← 兩條路都可能回 null
}
```

⇒ `HButtonSetting.icon` 的 ID 指到不存在的 sprite asset ⇒ `NullReferenceException` 在 `Init` 裡。

🩸 這格難看的地方是**那道 `if` 看起來像有防護**，而它站在解參考的**後面**一行。
⇒ 症狀不是「圖沒出來」，是**那顆按鈕的 Init 整個炸掉**（而 `HGameBase` 的生成迴圈沒有 try/catch ⇒
可能連後面幾顆按鈕都不會生成）。

📌 同檔對照組：`icon` 的預設值是 `new("RightButton_ShaSei")` ⇒ **預設值本身就是一個具體 ID**，
不是空字串 ⇒ 這條路的觸發條件是「asset 被改名／刪掉／沒進包」，不是「企劃忘了填」。

\## 改了什麼（`Assets/Scripts/UI/HButton.cs` `Init()`）

```csharp
var sprite = setting.icon?.GetData()?.Sprite;
if (sprite != null && image != null) image.sprite = sprite;
```

原本是 `setting.icon.GetData().Sprite` —— 那道 `if (sprite != null)` 擋的是 `Sprite` 為 null，
而它站在解參考的**後面**一行。

\## ⭐ 先數入口（判準⑧）—— 這一串上面不只一格會 null

| 入口 | 會不會真的是 null | 處置 |
|---|---|---|
| `setting.icon` | 預設值是 `new("RightButton_ShaSei")`，但反序列化可以留 null | `?.` |
| `GetData()` | **會**：`UCL_AssetEntry.cs:62-74` 兩條路都 `return null`（含 catch 之後） | `?.` |
| `.Sprite` | 會 | 原本那道 `if` |
| `image` | 會（Inspector 沒接）| 補上 —— ⚠ **這一格超出開單時的射程**，理由在下面 |

⭐ `?.` 在這裡**不是裝飾**：`GetData()` 走的是 `Util.GetAsset(ID, iUseCache) as T`，
`as` 失敗回的是**真 null**；而 `UCL_Asset<T>` 的約束是 `where T : class, ... new()`，
**不是 `UnityEngine.Object`** ⇒ 沒有 Unity 假 null 那格，`?.` 的語意是精確的。
（我特地去量這一格，是因為見叢裡躺著一條「`Ins?.Foo()` 那族的 `?.` 是裝飾」。這一支不是那一族。）

\## ⚠ 我擅自多守了一格（`image`），這件事我顯性講

`image` 為 null 跟 `sprite` 為 null 是**同一個失效形狀**，而同一個方法裡 `text` 本來就寫著
`if (text != null)` ⇒ 補 `image` 是**跟這支檔自己的慣例對齊**，不是我另立規矩。
⛔ 但它確實不在開單時寫下的證據裡 —— 誰覺得該退回只守 `GetData()` 那一格，說一聲我就收回。

\## 憑據（獨立編譯器／runtime 的形狀探針，前後並排）

```
── TASK-0190　icon.GetData() 解不到 asset ──
  BEFORE Icon_Old(entry)                 = **NullReferenceException**
  AFTER  Icon_New(entry)                 = null
  AFTER  Icon_New(null)〔反向對照〕          = null
```

替身的 `GetData()` 跟 `UCL_AssetEntry` 一樣**明確回 null**（不是丟例外）——
那正是這張單的成因：那道 `if (sprite != null)` 擋的是 `Sprite`，而它站在解參考的**後面**一行。

- **BEFORE 炸了** ⇒ 探針對準了成因。
- **反向對照**：`entry` 自己是 null 的那條路也不能炸 ⇒ 回 `null`，沒有例外。

\## ⭐ 順帶把「`?.` 是不是裝飾」那一格量掉了

見叢裡躺著一條血證：`XxxService.Ins?.Foo()` 那族的 `?.` 是**裝飾**（那支不會回 null，會丟例外）。
所以我沒有直接相信自己加的 `?.`：

- `UCL_AssetEntry.GetData()` 走 `Util.GetAsset(ID, iUseCache) as T` ⇒ `as` 失敗回**真 null**。
- `UCL_Asset<T>` 的泛型約束是 `where T : class, ... new()` ⇒ **不是 `UnityEngine.Object`**
  ⇒ 沒有 Unity 假 null 那一格，`?.` 的語意是精確的。

⇒ **這一支不屬於那一族。** 換句話說：我換的是問法，不是多試幾個 asset。

\## ⚠ 我多守的那一格（`image`），這裡結案

同一個方法裡 `text` 本來就寫著 `if (text != null)` ⇒ 補 `image` 是**跟這支檔自己的慣例對齊**。
早上我請人判要不要退回，到現在沒有人反對；我以 QA 身分判**留著**，理由是它與成因同族（同一行的解參考鏈），
而拆掉它會讓同一個方法裡兩個同形的欄位一個守一個不守。⛔ 誰之後不同意，退回我照改。
