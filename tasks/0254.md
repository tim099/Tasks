### 💬 #2 summit 2026-09-20T12:26:35.462Z
\## 根因：`s_FirstEntry` 的 regex 寫死 LF，而章檔是 CRLF

`SCP_WatchWriter.s_FirstEntry` = `^### \[seq (\d+)\][^\n]*\n\n(.{0,200})`。
章檔在 Windows 上是 CRLF ⇒ `[^\n]*` 先吃掉 `\r`，接著要求的 `\n` 撞到下一行的 `\r` ⇒ **永不匹配**。
守衛因此走進「沒有實錄段 ⇒ 無從核對」那一格，而那一格的文案接著建議跨區 seq。

\### 讀數（磁碟直讀）

`Books/watch-*/` 有實錄段的章檔 **45 個**：舊 regex 命中 **0**／修正後命中 **45**／全 CRLF **45**。
⇒ 不是 006／007 這兩章的事，是**每一章**。

\### 修正

`[^\r\n]*\r?\n\r?\n` —— SCP_Core `e7e3e48`（已 push；`Senate/SCP_Core` 已 `pull --ff-only` 同步、
`build.sh` 重出 exe、`check.sh --only watch` 四關全過）。

\### 驗收②的證言走的是另一條路（⛔ 不是我量 regex 那條）

重跑開單時那道**原始指令**（拿掉 `force`）：

- 修正前：`❌ 拒絕重出：既有章檔裡找不到任何一則實錄`
- 修正後：`❌ 006.txt 已存在 —— 拒絕重出（要 force）` ← **它已經通過身分核對，卡在下一道閘**

⇒ 這是一次真的執行，不是我自己的 regex 重算。

\### 🩸 順帶記一把壞尺

診斷時我用 `sed -n '19,23p' <章檔> | od -c` 看行尾，它印出**純 LF** ——
Git Bash 的 sed 在文字模式把 `\r` 吃掉了。我照那個讀數判過一次「行尾沒問題」。
⇒ **診斷行尾問題時，任何逐行讀的工具都可能先把證據正規化掉**；要整檔讀（`perl -0777` / 直接 `od -c` 對檔）。

\### 開單時排除的三個假說都排對了

章齡／跨區 seq／讀錯樹 —— 三個都不是。而三個排完真兇仍不在清單上，
因為**它不在「seq 對不對」這個維度上**。（見根 `lesson_enumerator_blind_spot` 又一筆。）
