## 任務描述

### 🔬 證據（開單時附；含「讀數怎麼拿到的」）

2026-09-23，TASK-0287 移植 quest 投影層時，用 Senate 側的真 JSON parser 跑同一份資料，與 Editor 輸出對拍才現形。

`UCL_ChatTavernQuestIO.ParseEvent`（UCL_Core，`:980`）逐字：`int dataIdx = line.IndexOf("\"data\":{");`
⇒ 它要求 `"data":` 後**緊接** `{`，中間**不可以有空格**。而磁碟上大量事件檔逐字是 `"data": {`（有一個空格）。

⇒ `dataIdx < 0` ⇒ `e.data` 保持 null ⇒ 那一筆事件的 **data 整包被丟掉**，而 `data` 是 optional 欄位 ⇒ **沒有任何一層會叫**。

## 讀數（全庫掃 `rooms/**/*__task_*.json`）

| 格式 | 檔數 | Editor 讀得到 |
|---|---:|---|
| `"data":{`（自家 `SerializeEvent` `:954` 寫的） | 468 | ✅ |
| `"data": {`（**別的寫入端**寫的） | **200** | ❌ |

⇒ **30% 的 quest 事件，data 被靜默丟掉。**

## 活體（room `tavern-entry-latency`，28 個 task）

`ucmd run Tavern op=task_list` ⇒ Role 欄**全部** `-`、Last Progress 欄**全部** `-`。
同一份資料走 Senate 側 `tavern-read kind=task_list`（真 parser）⇒ Role=`writer`/`programmer`/`planner`…、Last Progress 有內容。
磁碟原檔判誰對：`events/2026-05-08/231925_000000_3b2776__task_create.json` 逐字
`"data": {"title": "...", "role": "writer", "priority": "high", ...}` ⇒ **Senate 對，Editor 漏**。

## 🩸 傷害形狀

失效樣子是「那些欄位**剛好都是空的**」—— 一個完全合理的外觀。
`task_list` 的 Role／Last Progress、`task_state` 的 title／depends_on／lease_until 都靠 data ⇒
**接手者看到的是一張欄位齊全而內容被掏空的表**，而它不報錯、不警告、exit 0。

📌 成因可追：`ParseEvent` 檔頭 `:970` 自己寫著「**只認預期欄位順序（自家 SerializeEvent 寫出來的）**」——
那句話在寫的當下是誠實的。⇒ 病不在那一行，在**後來多了第二個寫入端**，而那句話沒有跟著失效、也沒有人會發現它失效了。

## 結單說明

**球在**：沒有人。8/8 勾滿，憑據 `UCL_Core 05f9788d`。

**修法**：`ParseEvent` 的 `IndexOf("\"data\":{")` 抽成 `IndexOfDataBrace` —— `"data"` 之後跳過**任意空白**找 `:`，再跳過任意空白找 `{`。⛔ 不是多比對一個帶空格的字面（那只把洞縮小一格）。

**逐格讀數**寫在 commit 訊息裡，⛔ 不在這裡重抄。四組：修前後差分（28 筆全 `-` → 28/28 有值）／磁碟原檔當基準（28/28 零不符）／全庫回歸（200 檔所在的 5 個房逐房驗）／反向對照（無空格批 17/17）。
