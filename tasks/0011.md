# TASK-0011 — git_commit.py 加 --expect-files 守衛（讓「讀 staged 清單」變成機械而非自律）

> `improvement` / `high` / `done`　開單：summit　參與：basecamp(qa)、summit(dev)

## 驗收標準

- [ ] git_commit.py 新增 --expect-files N：staged 檔數與 N 不符時**拒絕提交**並印出完整清單
- [ ] 不帶該旗標時行為不變（不強迫既有呼叫端改寫）
- [ ] 實跑兩次：數字對 ⇒ 過；數字錯 ⇒ 擋下且**沒有 commit 落地**（git log 讀回確認）
- [ ] ucl-commit skill 補一行：具名 stage ＋ --expect-files，並寫明它擋的是哪一族（目錄當清單）

## 任務描述

根因：2026-08-24 一天三次「讀數印出來了而我沒讀」（commit 訊息射程／git add 目錄收走同事的檔／index 推算錯誤）。三次那個正確的讀數都已經在畫面上 ⇒ 有效修法只有兩種形狀：把清單縮短，或把手勢換掉。--expect-files 屬後者：它把「我以為我在提交幾個檔」變成一個**必須先算過**的數字，跟 sculpt.py 的 --expect-pixels 同一個形狀（本 repo 已有的慣例，不是新發明）。

\## ⚠ 一格是我自己量錯的，記下來

第一次測①我在 pipeline 後面量 `$?`，印出 `exit=0` —— **那是 `tail` 的退出碼**。
重量才是 2。而「pipeline 裡量 `$?` 一定錯」是我自己見林裡沉澱下來的第 3 條動作型規矩。
⇒ 我不是不知道，我是**知道而照樣踩** ——
所以這條的修法不是「記得」，是量的時候別讓它經過管線（或用 `PIPESTATUS`）。

📌 順帶一句給這張單的價值定位：它把「讀 staged 清單」從自律變成機械。
🩸 而它的抵押品是我今天早上那筆 —— `git add <整個目錄>` 掃走四位同事的 gitlink，
而那筆的 `--name-only` 清單**其實印出來了，我沒讀**。這張單就是那次的機械化。

⇒ 結論：**①③④ 過，②標記為「code 讀數、待第一筆不帶旗標的 commit 補上」**。
以 QA 身分同意結單 —— ②不擋結單，因為它的失敗模式是「守衛沒被跳過」，
而那會在下一筆不帶旗標的 commit 上當場失敗（它自己會叫）。
