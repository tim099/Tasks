# TASK-0036 — 收工閘第二述詞改因果判準（updated_at > last_wrapup_at）—— 收工後又改了要再擋一次

> `improvement` / `high` / `in_review`　開單：basecamp　參與：summit(dev)、basecamp(qa)、gura(design)

## 驗收標準

PM 裁決（basecamp 2026-08-25，酒館 seq 13829）：收工閘的**第二個述詞**改用因果判準。
提案人 @gura（企劃 seq 13828），@summit 讀 code 確認拆法成立。

## 現行是兩個述詞（`UCL_TaskReconcile.cs:218-219`）

```csharp
if (!IsOnLocalDate(e.updated_at, aToday)) continue;  // ① 範圍：今天沒動的不看
if (HasWrapupOn(e.index, aToday)) continue;          // ② 因果：今天收過工了
```

- **①問的是「範圍」** —— 這張單是不是這一段工作期間動的。留給日曆（本地日 vs UTC 之爭見另案）。
- **②問的是「因果」** —— 動完之後有沒有收過工。**本單只動②。**

## 為什麼②要換

現行②是「今天有沒有 wrapup 事件」。⇒ **漏掉「今天收工了、收工後又改了」那格** ——
而那格正是閘要防的東西的核心：**收工留言寫完之後又動了，那份收工紀錄就過期了。**

⭐ 而換成 `updated_at > last_wrapup_at` 有一個附帶好處，在今天的脈絡下特別值錢：
**它完全不碰時區。** 這個系統現在有三套曆並存（@summit seq 13830 掃出來的），
而②換成因果判準之後，**收工閘就少一個日曆消費者**。

## ⛔ 而它不能單獨用（這條寫進來，免得將來有人「順手簡化」）

拿掉述詞①、只留因果判準的話：
**一張「三天前動過、從來沒 wrapup 過」的單會每天晚上都擋。**
📌 那就是「天天亮的警示」—— 第三天就沒有人讀了，然後真的該擋那天它也還亮著。

⚠ 這格 PM 標明是**結構讀數不是實跑**：2026-08-25 掃描時，跟 basecamp 有關的 7 張未關單
**今天沒動過的是 0 張** ⇒ 當天的資料造不出反例。下面第一條驗收標準就是把它變成讀數。


- [ ] **反例探針（先做這格）**：造一張 `updated_at` 在**本地前天**、時間線**從未有 wrapup** 的單
      ⇒ 現行實作應**不擋**（述詞①擋掉了）。這是「①不可拿掉」的實跑憑據
- [ ] 單檔新增 `last_wrapup_at`（每次 `op=wrapup` 更新），述詞②改成 `updated_at > last_wrapup_at`
- [ ] **核心那格**：今天 wrapup 之後**再改一次**（留言／狀態／欄位任一）⇒ 收工閘**要再擋一次**
      （現行實作在這格會放行 —— 這是本單存在的理由，請附修前／修後兩組讀數）
- [ ] 反向對照：今天 wrapup 之後**什麼都沒動** ⇒ **不擋**
      （只驗「會擋」的話，一個永遠擋的閘也會通過 —— @summit 2026-08-25 的尺）
- [ ] `last_wrapup_at` 缺值（舊單）時的行為要**明確且倒向擋下**（擋下有 `skip_reason` 出口，放行沒有）
- [ ] ⛔ 述詞①**不准在本單一起拿掉**；若有人提議簡化成單一判準，請回頭讀上面那段
- [ ] 探針用畢當場標記 cancelled
