- [ ] 明確判定目前是否能以每次動作的具體檔案與公開目的地授權放行；若不能由程式修復，文件說明限制與可行的安全替代流程
- [ ] 完成 ArtGallery 圖片 selector 介面草案：輸入形狀、`AgentCommands/ArtGallery` canonical root、解析輸出、缺檔／越界／符號連結／副檔名錯誤的阻擋行為
- [ ] 完成驗證矩陣：純文字、明確本地圖片、ArtGallery selector、無效或越界 selector、未帶 confirm；每項都定義不得意外公開上傳的反向判準
- [ ] 產出不改程式碼的實作拆解與影響範圍，明確列出需修改的 handler、技能文件與測試／回讀證據

## 任務描述

## 目的
釐清「Plurk 附圖公開發布」這次實際被哪一層擋下，並評估是否需要讓 Plurk 交付單直接指定 ArtGallery 內的圖片，避免每次填寫完整絕對路徑。本 Task 只做事故分析、介面與安全邊界設計；本回合不修改程式碼、不重新嘗試公開上傳圖片。

## 已知證據
- `op=lint` 已通過：文案 95 字、附圖上限 240 字、公開度「所有人」均符合形式檢查。
- 帶本地 ArtGallery 圖片的 `op=post --confirm=1` 在終端程序建立前，被外層安全審查拒絕；回覆明確指出「本地 ArtGallery 插圖及其衍生閱讀內容公開上傳」屬於未具體授權的外傳風險。
- 因此該次沒有進入 Senate、Unity `Cmd_Plurk`、`uploadPicture` 或 Plurk API；不能把它誤判成圖片格式、OAuth、Watcher 或 Plurk HTTP 錯誤。
- 移除圖片後的同一則文字噗已由 Senate/Unity/Plurk API 成功送出，HTTP 200，取得 plurk id `358750147555661`；這只能證明文字發布路徑正常，不能證明圖片上傳分支正常。
- 目前 `Cmd_Plurk` 的圖片路徑契約是絕對路徑；`post` 會在送正文前先呼叫 `uploadPicture`，取回 URL 後再把 URL 併入 content。

## 待分析決策
1. 安全閘門是否只能透過每次公開動作明確指定「哪個檔案、要公開傳到哪裡」來放行；確認程式別名不能也不應繞過此授權邊界。
2. 若保留便利性，定義 ArtGallery selector 的穩定契約：建議採相對於 `AgentCommands/ArtGallery` 的相對路徑或展品 ID，由程式解析成絕對路徑；不接受任意相對工作目錄。
3. 定義解析安全界線：拒絕 `..` 穿越、絕對路徑越界、符號連結越界、缺檔與不支援副檔名；lint/preview 要印出實際解析結果，post 仍保留 confirm。
4. 分清「降低路徑填寫摩擦」與「允許公開外傳」是兩個獨立問題；selector 不得被描述成安全閘門修復。
