## 任務描述

### 🔬 證據（開單時附；含「讀數怎麼拿到的」）

## 症狀

`_cmd_slow.jsonl` 的 `kind=freeze` 行讀起來是「主執行緒凍結 N 毫秒」，
而其中有一大批**沒有任何 cmd 在跑**、且跨天規律出現 —— 那批更像 **Editor 閒置／失焦時 `EditorApplication.update` 被節流**，
不是主緒被工作卡住。⇒ **兩件處置完全相反的事，在這個欄位上長得一模一樣。**

## 🔬 讀數（2026-09-10，本機一份檔）

| 讀數 | 值 |
|---|---|
| 檔內 `kind=freeze` 行 | **289** 筆（09-08T12:53Z 起） |
| 2026-09-10 觀影場（13:xxZ） | 64 筆，其中 **7 筆 `running_cmds` 為空** |
| 與觀影場無關的其餘 | 225 筆，其中 **36 筆 `running_cmds` 為空** |
| `frozen_ms` 分布 | 全部落在 **3001–3766ms**，而 `threshold_ms=3000` ⇒ **幾乎全部剛過門檻** |
| 觀測者 | `observed_from_tid=475`（背景 watchdog，每 N 秒回讀主緒心跳） |

⇒ 「零 cmd 在跑」那 43 筆是關鍵：**沒有任何工作在主緒上，而它照樣被判成凍結。**

## 為什麼它值得一張單（不是順手修）

它**已經害我今天判錯兩次**：TASK-0120 ④ 我一度把這批凍結讀成「offload 之後主緒仍被 handler 卡住」，
而正確讀法是「這批凍結跟 handler 無關」。⇒ 這個欄位現在會把**看它的人推向錯的成因**，
而它的失效樣子是**有內容、有時間戳、格式完整**。

## ⛔ 射程

- 只動 freeze 那條路徑的**判定與欄位**（`UCL_AgentCmdMainThreadWatchdog`）。
- ⛔ 不動 `kind=cmd` / `kind=stall` 的語意，⛔ 不動門檻常數當作「修好」（調高只是讓它少叫）。
- ⚠ 「Editor 失焦時 update 被節流」是**我的首選假設，不是量到的成因** —— 本單第一步就是去量它（是否 focused／低 CPU 模式）。

| 隱含假設：`running_cmds` 空 ⇒ 閒置 | ❌ **不是分辨鍵** —— 「有 cmd 在跑」那批**也有 748 行主緒仍在前進** |

## ② 真正的分辨鍵（而它用現有欄位就算得到，只是要跨行）

**主緒有沒有前進**：`last_main_tick_at` 每行都變 ⇒ 沒被卡（1203/1470 ＝ **82%**）；
同一個 tick 被連報 ⇒ 真的停住（266 行，只集中在 **67 次**事件）。
⇒ 修法就是把它放進同一行：`same_tick_reports` ＋ `prev_tick_gap_ms`。

## ③ 兩半都有活體

- **真卡住**（用 TASK-0172 今天剛修好的 `Cmd_Invoke` 在主緒 `Thread.Sleep(15000)`）：
  同一個 tick `02:58:59.269Z` **被連報兩次** ⇒ `same_tick_reports: 1 → 2`。
- **閒置那半**（自然產生、非我造）：`03:01:10` / `03:01:19` / `03:01:33` 三行
  （其中兩行 `running_cmds` 空）⇒ **全部 `same_tick_reports = 1`，一行都沒有升到 2**
  ⇒ 讀起來不再像「主緒被卡」。
- ⭐ 天然對照：`02:58:15` 那行（recompile 期間、**舊版 code 寫的**）兩個新欄位都是 `null`。

## ⚠ 而有一格我預期錯了，照實記（⛔ 不寫成成功）

我加 `prev_tick_gap_ms` 時的預期是「閒置節流 ⇒ 幀距本來就很大（3 秒級）」。
**實測五行全部是 99.3 / 99.3 / 99.3 / 99.7 / 99.9 ms** —— 包括我造的那兩行真凍結。
⇒ **這個欄位在本次樣本中沒有分辨出兩者。**

📌 而那個 ~100ms 本身是一個讀數：Editor 當時處在 **~10Hz 的低頻模式**（有焦點時該是 ~16ms）。
⇒ 所以它給的是「Editor 當時的基礎頻率」這個 context，⛔ **不是分辨鍵**。
⚠ 它要在「幀距本來就到 3 秒級」的場景才驗得到用處，而**我今天沒有那種樣本**。
⛔ 我不刪它（它是便宜的 context 且已落盤），⛔ 也不宣稱它有效。

## ⛔ 這張單沒有做到的

- **成因仍未宣告**：「Editor 失焦被節流」從開單到現在都是**首選假設**。
  我沒有 `focused` 的歷史欄位可回頭對，本筆也沒加（加了也只能解釋未來的行）。
  ⇒ 本單交付的是「**讀數分得出來**」，⛔ 不是「成因查明」。
- **沒有真正的長幀距樣本**（見上）⇒ `prev_tick_gap_ms` 的用處**未驗**。
  ⇒ 補它的時機＋動作：哪天在 freeze 行上看到 `prev_tick_gap_ms` 是千位數，
  那一行就是它的第一個活體 —— 到時回來把這格補上讀數，⛔ 別重開本單。
- ⛔ 沒動 `frozen_ms` / `running_cmds` / `threshold_ms` 的語意，⛔ 沒調門檻當作修好。

## ⛔ 已知限制（留在 code 註解裡，不被蓋掉）

**一次凍結的第一行本來就分不出** —— `same_tick_reports` 那時必然是 1，要等它會不會再報一次。
⛔ 不用一個猜出來的 `cause` 欄位把這個限制蓋掉：那會變成「在寫入端替讀者下結論」，
而本單開單時的 ⛔ 射程就明寫著不准那樣做。
