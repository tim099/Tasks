### 🔬 證據（開單時附；含「讀數怎麼拿到的」）

## 症狀

`_cmd_slow.jsonl` 的 `kind=freeze` 行讀起來是「主執行緒凍結 N 毫秒」，
而其中有一大批**沒有任何 cmd 在跑**、且跨天規律出現 —— 那批更像 **Editor 閒置／失焦時 `EditorApplication.update` 被節流**，
不是主緒被工作卡住。⇒ **兩件處置完全相反的事，在這個欄位上長得一模一樣。**

## 🔬 讀數（2026-09-10，本機一份檔）

| 讀數 | 值 |
|---|---|
| 檔內 `kind=freeze` 行 | **289** 筆（09-08T12:53Z 起） |
| 2026-09-10 觀影場（13:xxZ） | 64 筆，其中 **7 筆 `running_cmds` 為空** |
| 與觀影場無關的其餘 | 225 筆，其中 **36 筆 `running_cmds` 為空** |
| `frozen_ms` 分布 | 全部落在 **3001–3766ms**，而 `threshold_ms=3000` ⇒ **幾乎全部剛過門檻** |
| 觀測者 | `observed_from_tid=475`（背景 watchdog，每 N 秒回讀主緒心跳） |

⇒ 「零 cmd 在跑」那 43 筆是關鍵：**沒有任何工作在主緒上，而它照樣被判成凍結。**

## 為什麼它值得一張單（不是順手修）

它**已經害我今天判錯兩次**：TASK-0120 ④ 我一度把這批凍結讀成「offload 之後主緒仍被 handler 卡住」，
而正確讀法是「這批凍結跟 handler 無關」。⇒ 這個欄位現在會把**看它的人推向錯的成因**，
而它的失效樣子是**有內容、有時間戳、格式完整**。

## ⛔ 射程

- 只動 freeze 那條路徑的**判定與欄位**（`UCL_AgentCmdMainThreadWatchdog`）。
- ⛔ 不動 `kind=cmd` / `kind=stall` 的語意，⛔ 不動門檻常數當作「修好」（調高只是讓它少叫）。
- ⚠ 「Editor 失焦時 update 被節流」是**我的首選假設，不是量到的成因** —— 本單第一步就是去量它（是否 focused／低 CPU 模式）。
