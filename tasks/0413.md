# TASK-0413 — 長時間的 tavern-wait 握著 publish/senate.exe ⇒ 別人出廠撞 access denied，要到酒館一個一個請人停

> `improvement` / `normal` / `todo`　開單：basecamp　⚠ **尚無參與者**（沒有人在做這件事）

## 驗收標準

- [ ] 有一支 `tavern-wait` 在跑時出廠成功，不撞 access denied（或撞到時印出是誰、哪個 pid 握著）
- [ ] 正在跑的 wait 不會因為出廠而丟結果，或丟的時候會出聲

## 任務描述

所有 agent 都用同一顆 `publish/senate.exe`，而早安、叮、自由時間的流程都會叫 agent 開長時間的 `tavern-wait`（數分鐘到數十分鐘）。
只要還有任何一支從那顆 exe 跑起來、還沒結束，出廠覆寫就會撞 access denied，出廠的人得到酒館一個一個去請人停手。
可能的方向（由 Tim 選）：
- (a) 出廠改成「寫新檔＋改名換掉」（Windows 允許改名執行中的 exe），不再直接覆寫；
- (b) 長等待類的 Cmd 改成會偵測出廠旗標、自己提早結束；
- (c) 出廠前列出握著 exe 的 pid 與 persona，至少讓出廠的人一眼看出要找誰。

### 🔬 證據（開單時附；含「讀數怎麼拿到的」）

讀數（2026-10-06，LY）：
- 08:46 basecamp 在背景開 `senate cmd tavern-wait --arg timeout=1500 --arg mention=1`（文件建議 agent 用長等待等人回話）。
- 08:51:47 summit（seq 21800）：重出廠 senate.exe（TASK-0406）時 publish 撞 access denied ——「妳的 tavern-wait（pid 57284，08:46 開的 1500 秒）正握著 publish/senate.exe」。
- 這次會解開，只是因為 summit 那一則剛好 @ 到等待中的 basecamp，把 wait 叫醒結束了（exit 0，等了 321.7s）。如果她沒 @ 到我，或等的人不是被 @ 的那位，exe 要被握滿 25 分鐘。
⚠ 射程：只量到這一次，是 summit 回報的；我沒有自己重現 access denied。
