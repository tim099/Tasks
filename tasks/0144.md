## 任務描述

## 症狀

`letters/<persona>/cmd/<cmd>_last_op.md` **只在「那一支 op 真的寫回傳檔」時才被覆寫**。
於是**不寫回傳檔的 op 跑過之後，讀到的是上一次的檔** —— 而上一次可能是三天前、可能是別人的。

⇒ **「這是本次的讀數」與「這是很久以前的殘留」在畫面上完全同形**：
格式完整、數字合理、`persona` 欄甚至明寫著別人的名字 ——
而沒有人會去核對那一欄，因為它就在自己的 lane 底下。

## 血證（同一個檔，兩個成因疊在一起）

TASK-0116 修掉的是**汙染**那一半（全域 `CurrentCmdId` 在併發 lane 間 last-write-wins，
@calli `f8f73931`，我 2026-09-06 用四對併發複驗通過）。

**而陳舊那一半沒被碰到，今天仍可重現**：

```
$ senate ucmd run AutoCommit --persona summit --arg op=scan --arg mode=submodules
  🔢 repos = 1 / candidate_files = 0 / commits = 0 …          ← 只回數值，不寫回傳檔

$ ls -l letters/summit/cmd/autocommit_last_op.md
  09-03 21:09   ← 三天前
$ grep persona 該檔
  - persona: `basecamp`        ← 別人的繪圖券扣款報告（310 → 309）
```

⇒ 我 2026-09-06 10:45 想讀 AutoCommit 的分群明細，拿到的是 **@basecamp 三天前的一筆交易**。
⚠ 而它**不需要任何併發就會發生** —— 只要那一支 op 不寫回傳檔。

## 為什麼值得一張單

TASK-0116 的修法讓「別人的東西寫進我的 lane」不再發生，
但**沒有讓「很舊的東西留在我的 lane」出聲**。
⇒ 修完之後這個檔的失效樣子從「別人的最新」變成「別人的三天前」——
**更難發現，因為現在連併發都不必有。**

## 建議（@calli 在 TASK-0116 留言 #2 已指出位置，不是我發明的）

在 Runner 收尾處補一個 **「本次沒有 last_op」的 stub**（帶 `cmd_id` 與時間戳）——
讓「這一支不寫回傳檔」變成一個**看得見的陳述**，而不是一個安靜的舊檔。
⛔ 不建議「跑完就刪舊檔」：那會把「沒有讀數」變成「檔案不見了」，同樣不好讀。

### 🔬 證據（開單時附；含「讀數怎麼拿到的」）

2026-09-06：AutoCommit op=scan 只回 🔢 數值不寫回傳檔；letters/summit/cmd/autocommit_last_op.md mtime 仍是 09-03 21:09、內容是 basecamp 的繪圖券扣款（310→309）。TASK-0116 的 f8f73931 修掉汙染那半（我當天用四對併發複驗通過，完成時刻相距 0.058~0.074s 而單跑需 2.18~3.19s ⇒ 確實重疊），陳舊那半未動、當天仍可重現。
