### 🔬 證據（開單時附；含「讀數怎麼拿到的」）

## 🔬 活體讀數（2026-09-15 09:4x，對 build 後的 `publish/senate.exe`）

```
$ ./publish/senate.exe ui --page sessions          ⇒ 印出「路徑管理」頁
$ ./publish/senate.exe ui --page zzz-not-a-page    ⇒ 也印出「路徑管理」頁，**一個字都沒說**
$ ./publish/senate.exe ui --help                   ⇒ `--page` 明列在合法旗標裡
```

⇒ **文字模式下 `--page` 給什麼都一樣，包含一個保證不存在的 key。**

## 讀了什麼（成因，不是推的）

`src/Senate.Cli/Program.cs:363` 的 `--page` 處理**住在視窗模式那條路**（`RunWindow`），
而它自己的註解寫著存在的理由是驗收：

> 「視窗裡的頁面本來只有人點得到（截圖模式沒有點擊入口），於是『那一頁在視窗裡畫不畫得出來』就沒有讀數。」

同一段甚至**已經處理過這隻病的視窗版**：

```csharp
if (aTarget == null) { …印認不得的頁面 key ＋ 現有清單…
    return 2;   // 靜默開在首頁會讓「打錯 key」與「那頁是空的」同形
}
```

⇒ 🩸 **那行註解描述的正是文字模式現在的行為。** 防線寫好了、理由寫對了，
只是文字模式那條 render 路徑從來沒讀過這個旗標，於是同一顆 exe 上
**同一個旗標有兩種語意：視窗模式 exit 2，文字模式靜默忽略。**

## 為什麼值得一張單（三個判準都中）

- **會再犯**：`--page` 是驗收用旗標，而 agent 驗收幾乎都在文字模式（stdout 不是終端機）。
- **失敗是靜默的**：沒有 exit code、沒有 stderr，畫面看起來完全正常 ——
  它只是**畫了另一頁**，而那一頁自己長得很健康。
- 🩸 **我今天就付了**：我要驗自己剛改的 `sessions` 頁，連下兩次都拿到 `paths` 頁的內容。
  第一反應是「我的頁面改壞了 / 沒註冊」—— 而 `SenatePages.cs:41` 好好註冊著。
  ⇒ 擋下我的是我去餵了一個**保證不存在的 key**（w66 那條：臨時搭的尺先餵已知答案），
  不是我更仔細。

## ⇒ 修法方向（⛔ 我沒做，也不主張這是唯一解）

把那段「解不出 key ⇒ 印清單 ＋ return 2」搬到**兩條路共用的前置**，
讓文字模式也吃 `--page`（或至少：文字模式收到 `--page` 就明說「本模式不支援，用 `--click home/open/<key>`」）。
⛔ 而「兩條路各自實作一次」正是它變成今天這樣的成因，不要再複製一份。

## ⛔ 我沒有做的事

- **一行 code 都沒改**（本單只開單）。
- 沒有去數 `ui` 其餘旗標（`--click` / `--set` / `--fold`…）有沒有同一種**兩條路不同語意**的分裂 ——
  只量了 `--page` 這一格。
