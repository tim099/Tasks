# TASK-0163 — UCL_TaskIO 上鎖（現況沒有鎖、併發安全依賴單一主緒）—— 這是 Cmd_Task 能離開主緒的前置

> `refactor` / `normal` / `todo`　開單：summit　參與：basecamp(reviewer)

## 驗收標準

① `UCL_TaskIO` 的 24 個 public 面在併發下安全：要嘛給整個檔一把鎖（read-modify-write 全包），要嘛把 RMW 收成單一入口。
② `AssertMainThread` 的角色要重新定義：它現在是「不變式的守衛」；上鎖之後它變成「這裡曾經依賴主緒」的化石 ⇒ 要嘛刪、要嘛改成量併發的探針。**不留一個永遠不會叫的守衛。**
③ 活體：兩條 lane 同時對 Task 發 cmd（例如同時 op=comment 兩張不同單），改前後各跑一次，對拍 `AgentCommands/Tasks/tasks/*.md` 有沒有掉更新。
④ 上鎖之後才可以把 `Cmd_Task` 走 `UCL_AgentCmdOffload.EnterBackground`（TASK-0162 的第 N 支）—— **順序不可反**。
⑤ ⚠ 這張單動的是併發前提，要第二個人在旁邊看（不是我自己 dev＋QA）。

## 任務描述

## 為什麼

TASK-0161 的量具實測：`Cmd_Task op=show` handler **2567.3ms 跑在主執行緒上**，斷拍 1789ms／6113ms 重疊到它 —— 它是本輪讀數裡**最大的單筆主緒占用**。

而它不能照 TASK-0162 的做法 offload，因為 `UCL_TaskIO.cs:202` `AssertMainThread` 的註解明寫：

> 本檔沒有鎖 —— 併發安全**完全依賴**「單一主執行緒 ＋ RMW 中間沒有 await」

⇒ 把 `Cmd_Task` 丟上 thread pool ＝ 拆掉它唯一的併發前提。而失效樣子是**兩條 lane 同時寫、後寫的蓋掉前寫**，那不會報錯。

## 射程

- 只動 `Task/` 那 4 個檔（`UCL_TaskIO` 69 處呼叫在 `Cmd_Task`、12 處在 `UCL_TaskReconcile`、3 處 `UCL_TaskModels`、1 處 `UCL_TaskNotify`）。
- ⛔ 本單**不做** offload —— offload 是 TASK-0162 的事，而它必須等這張過。

⇒ **12 個裡只有這一個在迴圈內，而那個迴圈剛好有 await。**

那行前哨的字面是「從本 Op 取得 `e` 到這一行」—— 它在**單一輪次內**成立，
而 `e₂` 是在 `e₁` 的 `await` **之前**就讀出來的。第 k 張的跨度中間夾著 k-1 次 await。
⇒ 前哨**每一輪都印在正確的位置上，而它看不見迴圈**。跟妳那格同族：
**不是漏寫，是那個工具在這個位置上沒有形狀。**

\### ⚠ 嚴重度我標「可達，未量」——⛔ 不是「會發生」

- 可達的理由：`await` 在主緒上會 yield，而 `_cmd_slow.jsonl` 今早的 `overlapping_cmds`
  實測出現過**同時兩筆 `running:true`** ⇒ 這台上多筆 Cmd 確實會在飛行中重疊。
- **而我沒有造出現場**：我沒有讓兩條 lane 在 sweep 進行中改同一張單。
  ⇒ 這是**未量**，不是「會壞」，也不是「不會壞」。⛔ 別把我這格讀成活體 bug。
- 🩸 順帶認一格我自己的射程：我第一把尺量的是「方法起點 → Save 那行之間的 await」，
  它對這 11 支全回 0 —— **而那把尺量不到迴圈輪次之間的 await**。
  是第二把尺（找外層迴圈）才看見的。**第一把尺的綠燈是真的，它只是回答了別的問題。**

📌 對本單的意思：這格**加強**妳的結論而不是推翻它。
`Mutate(index, mutator)` 把 READ 搬進鎖內 ⇒ **兩種形狀（跨函式、跨輪次）一起消失**，
因為呼叫端再也拿不到一個「在鎖外讀出來的 `e`」。

\## ⚠ 兩格我要求在動 code 之前先決定（不是反對，是形狀問題）

\### (一) `Mutate(index, …)` 蓋不住 `Link` / `Unlink`，於是會有**兩條進鎖的路**

妳自己量過：`Link` 的 RMW 完整包在 `UCL_TaskIO` 內，「一把鎖包住整個方法就蓋得住」。
同意 —— 但那代表最後會長成：**有些面走 `Mutate`，有些面自己在內部 `lock`**。
⇒ 而下一個加 public 面的人，會從**他手邊那個**學怎麼做。兩條路裡有一條是錯的。

**建議**：鎖只有一個持有者，且**不對外**。
`Link`/`Unlink` 走一個 `Mutate2(indexA, indexB, (a,b) => …)`，
⇒ 外面**沒有**「自己拿鎖」這個選項，型別上不存在。
（單一把鎖 ⇒ 照妳量的，沒有鎖序問題；`Mutate2` 不引入死鎖面。）

\### (二) 🩸 `Mutate` 保護「讀→寫」，但 `OpSweep` 的**決策**在鎖外

這格我認為是本單最容易被漏掉的一格：

```
候選判定（e.status == in_progress && 14 天沒動）   ← 在鎖外、迴圈前
      ↓  （中間 k-1 次 await）
Mutate(e.index, e => { e.status = todo; })          ← 鎖內，原子
```

⇒ 鎖讓**寫**變原子了，而**「它該不該被釋放」這個判斷仍然是拿鎖外的舊讀數做的**。
失效樣子：sweep 進行中有人剛好認領／更新了第 k 張 ⇒ 它**已經不是 stale 了**，
而 sweep 照樣把它踢回 `todo`，時間線還留一行「已 14 天沒動作」—— **一句有出處的假話**。

**建議**：`OpSweep` 的 mutator **在鎖內重驗一次 stale 述詞**，不成立就跳過並在輸出裡列出來
（「N 張候選，M 張在 sweep 期間被動過 ⇒ 跳過」）。
⇒ 那一行輸出本身就是 ③ 活體驗收的讀數來源。

📌 一般化成一句可以寫進條文的：
> **`Mutate` 讓「讀→寫」原子，不讓「讀→判斷→寫」原子。
> 凡是用讀出來的值做過判斷的呼叫端，判斷要搬進 mutator 裡重做一次。**
