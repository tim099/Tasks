# TASK-0063 — [文件] 熱點嵌套細切：更細的熱點就是更短的時間段（不擋重疊、無層級）

> `feature` / `normal` / `todo`　開單：basecamp　參與：summit(qa)

## 驗收標準

本單要傳達的全部內容就一句：
**熱點＝一個時間段；要更細就標一段更短的；系統不擋重疊與包含；沒有層級概念，也不需要有。**

- [ ] `ucl-stream-watch` skill 熱點段補上「**更細的熱點就是更短的時間段**」——
      明說可以在既有熱點區間內再標一段，不需要任何父子欄位或標註慣例
- [ ] **四份安裝副本位元組相同**（`cmp` 驗，不是目視；行尾一致）
- [ ] `StreamWatch_Cmd_Reference.md` 的 `step=hotspot` 段明寫
      「**不擋重疊與包含 ⇒ 嵌套是支援的用法，不是漏擋**」
      📌 目的是防下一個讀 code 的人把「沒有守衛」當 bug 去補一個守衛，那會剛好把這用法擋掉
- [ ] 文件**不得**引入 `parent_id` / `depth` / 層級編號（`H1.1` 之類）或任何「要標註母區間」的慣例
      —— 包含關係由時間戳自然可見，另存一份就是同一個量兩個說法
- [ ] 實跑一次嵌套熱點（母 20s、子 6s 落在其內）⇒ 兩筆都成功建立
      （本單唯一的「跑」，用來證明文件沒有寫出一個做不到的用法）
- [ ] `grep` 確認文件與本單敘述裡沒有殘留 `parent_id` / `depth` / `H<n>.<m>` 之類的舊設計

## 任務描述

## 需求（Tim 2026-08-26）
> 熱點中如果發現關鍵片段，可以追加更細切片的熱點
> （例如 20 秒熱點，發現打鬥或是精彩片段，再標一段 6 秒細看）。

## 為什麼值得做
它把熱點從「**標記**」升級成「**可以逐層對焦的動作**」：
主線用檔位跑 30–45s 粗格 → 熱點 20s 中格 → 子熱點 6s 細格。**同一個機制、三種解析度。**
（現行 `step=hotspot` / `step=claim` 只有單層，發現「熱點裡還有熱點」時無處可記，
 只能另開一個平行熱點 —— 於是「這是那段裡面的細節」這個關係就消失了。）

## 要做的
`UCL_StreamWatchHotspot` 現有欄位：`id / from_epoch / to_epoch / why / opened_by / opened_at / claimed_by / claimed_at`。
新增：
- `parent_id`（子熱點指向母熱點；空＝頂層）
- `depth`（層級；主線＝0、頂層熱點＝1、子熱點＝2…）
- 子熱點的 `from/to` **必須落在母熱點區間內** ⇒ 越界就 **blocked 並印出母區間**
  ⚠ **不要靜默夾住** —— 夾住之後看起來會像成功，而使用者要的那幾秒已經被吃掉了
  （「白即空白」同族：合法輸入與被修正的輸入必須可分）
- 編號：熱點**不吃主線段號**，用 `H<n>`，子熱點 `H<n>.<m>`
  理由見 TASK-0060 —— 保序機制要靠「主線缺號＝有段沒交」當訊號，那個訊號不能被合法行為污染

## 順帶要想的（不一定這單做）
- 母熱點已被認領／已結案時，還能不能加子熱點？（我傾向可以 —— 細看往往發生在看完之後）
- 子熱點的計酬是否與頂層熱點同價（6s 的細看跟 20s 的細看勞動量不同）

\## 📌 Tim 2026-08-26 22:02 拍板：**這件事改文件即可，不動 code**

> 「63 的話，我認為改文件即可。」

⇒ 本單從「新增 `parent_id`／`depth` 欄位」降級為**純文件單**。這是 §0.5 四階梯的 **Q1**
（現有架構做得到類似效果 ⇒ 不開新機制、不造新輪子），而且**有 code 讀數支持**：

`Cmd_StreamWatch.StepHotspot` 目前只擋兩件事：
1. 區間解析失敗或首尾顛倒（`to` 必須晚於 `from`）
2. `why` 為空（「未說明為什麼值得細看」）

**沒有任何重疊／包含守衛。** ⇒ 在既有 20s 熱點區間內再開一段 6s 熱點，**今天直接可用**，
不需要任何新欄位、不需要改 Cmd。

\## ⚠ 這個取捨放棄了什麼（要寫清楚，否則以後有人會以為是漏做）
父子關係**不是機器可讀的** —— 沒有 `parent_id`／`depth`，
所以「這個 6 秒是那個 20 秒裡面的細節」這層資訊不存在於資料結構裡。
影響的是將來若要做：熱點覆蓋率統計、母熱點結案時檢查子熱點是否都被領、按層級渲染。
⇒ 那幾件事**目前沒有人在等**，所以不值得現在為它們加欄位（同一條 Q1 判準）。

\## ✅ 而有一個零成本的緩解，文件要寫進去
`why` 是**必填**（空的會被 blocked）⇒ **把父子關係寫進 `why`**，資訊就存在於一個「不可能為空」的欄位裡。

建議寫法（文件要給範例）：
```bash
\# 母熱點（20s）
--arg from=20:57:51 --arg to=20:58:11 --arg why="密室推理整段，資訊密度高"
\# 子熱點（6s，落在上面區間內）
--arg from=20:58:02 --arg to=20:58:08 --arg why="[細看 20:57:51–20:58:11 內] 那句只有 STT 聽到的『藏起來吧』，要逐格對畫面字幕"
```
⇒ 慣例：子熱點的 `why` 以 `[細看 <母區間>內]` 起頭。**可 grep、不需要新欄位、不會漂**
（因為它跟那個熱點綁在同一筆記錄裡）。

\## 文件要改哪些（本單的實際交付）
1. `ucl-stream-watch` skill —— 熱點那段補「熱點可再切更細的子熱點」與上面的 `why` 慣例
   ⚠ **四份安裝副本要同步**（`.claude` / `.agents` / `.codex` / `Skills~`），
   而「四份位元組相同」是驗收項 —— 這族坑我自己踩過（`newline="\n"` 把不一致修成另一種不一致）。
2. `StreamWatch_Cmd_Reference.md` 的 `step=hotspot` 段 —— 明寫「**不擋重疊與包含**，
   所以嵌套熱點是支援的用法，不是漏擋」。
   📌 這一行很重要：**沒寫的話，下一個讀 code 的人會把「沒有守衛」當成 bug 去補一個守衛**，
   而那正好會把這個用法擋掉。
3. 三份文件都要標「父子關係不入資料結構」的取捨與理由（見上），避免被當成待補的洞。

\## 🩸 而我自己開的驗收條文有一條是錯的，在這裡更正

我原本寫「**四份安裝副本位元組相同**」。**那是錯的** ——
`install_skills.py` 對 `--target antigravity` 會**刻意注入**一行 `trigger: { on_intent: [...] }`
（`.agents` 天生比其他三份多那一行）。
⇒ 照我原本的條文驗，QA 會在一個**設計行為**上判失敗。

**正確的條文（以此為準）**：
- `.claude` / `.codex` / `Skills~` **三份位元組相同**（`cmp` 實測）
- `.agents` 與它們的差異**恰好只有注入的那一行**（`diff | grep -c '^[<>]'` ＝ **1**）

實測讀數（剛跑完）：
```
.claude   14124 bytes
.codex    14124 bytes   cmp claude==codex ✅
Skills~   14124 bytes   cmp claude==Skills~ ✅
.agents   14483 bytes   diff 行數 = 1（注入的 trigger 行）
```
⚠ 另外安裝器**一次只寫一個 target**（預設 claude）⇒ 要跑三次
（`--target antigravity`、`--target codex`）。只跑一次會靜默只更新 `.claude` ——
我第一次就是這樣，`copied=1` 看起來像成功。
