- [ ] 開新場次時 scratch 被清，且清除發生在 settle 之後（與 TASK-0065 的順序不衝突）

## 任務描述

## 狀態：**Tim 2026-08-26 22:00 拍板「暫時先不做，之後再處理」** —— 本單是記錄，不是待辦
> 「那暫時先不做接續（這部分感覺要重構蠻多）。目前中斷的話就直接結算（之後重頭看一輪），
> 等之後再處理中斷續看。」

## 需求（將來要做的）
觀影中途 Editor 出問題（不限 compile）⇒ **同一場**能接回來繼續看，而不是整場作廢重頭看。
Tim 補的關鍵約束：**中斷後 Editor 內 static 欄位與 in-memory 資料全掉，只能讀檔。**

## 設計輸入（Tim：參考 `UCL_ProcessRegistryService`）
可抄：每場一檔（避免併發互蓋、單檔壞不連坐）／落主專案 `AgentCommands/` 底下不入 UCL_Core／
清理有明確觸發點。
**不能抄**其死亡判定（`pid + process_name + start_time_utc` 三重比對）—— 觀影 session 背後**沒有 process**，
agent 是 LLM session。可驗的死亡證明只有現行 cycle 收工判定用的兩個顯式狀態：
① `end_ts` 已過 ② `_screenstream/_config.json` 的 `enabled=false`（錄影狀態本來就是寫檔的）。
⚠ 不得用 frame 新鮮度推論（現行 cycle 註解自己就寫「只認顯式狀態」）。

## 兩個時點必須分開（最容易被混成一件事）
| 事件 | 記憶體 | scratch 檔 |
|---|---|---|
| 中斷後接續（同一場） | 全掉，只能讀檔 | **留著**，靠它接回 |
| 開新場次（Tim 口中的「重啟」） | — | 清除（先 settle 再清） |

## 現況盤點（動工前先讀這段，可能比想像的小）
StreamWatch **大部分狀態已經在檔上**：
`sessions/<persona>.json`（cursor_epoch／cycles／last_cycle_ts／tavern_seq／start_seq）、
`relay/<primary>.json`（前緣）、`_screenstream/_config.json`（錄影狀態）、
`hotspots.json`、`sessions_log.jsonl`。
真正只活在記憶體的是：① Editor 內的等待迴圈（可由 `last_cycle_ts` 重算 —— 本來就是檔）
② `observe_queue`（TASK-0062，尚未實作）。
⇒ 所以「接續」的真正難點大概不是狀態持久化，而是**跑在 Editor 內的 async 流程被切斷後如何重新進入**。
動工前先量這一格，不要一開始就設計檔格式。

## 為什麼現在不做（值得留著的理由）
「中斷即結算」（TASK-0065）已經把兩個真正在漏的洞補掉：酬勞蒸發、seq 區間消失匯不進書。
⇒ 接續只影響「要不要重頭看一輪」的體驗成本。**用不到的正確性比用得到的複雜度值錢。**
