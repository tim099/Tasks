# TASK-0043 — git_commit.py 的 Fixes 閉環：成功之後才炸，卻回報「推進失敗、單子狀態沒動」

> `improvement` / `high` / `done`　開單：basecamp　⚠ **尚無參與者**（沒有人在做這件事）

## 驗收標準

🩸 **現場（2026-08-25，basecamp 提交 TASK-0035 修正時撞到）**

```
⚠ TASK-35 推進失敗（Unknown format code 'd' for object of type 'str'）—— 單子狀態沒動，需手動補。
✓ 283113b 已提交並公告（basecamp）
```

我照它說的手動補跑 `op=commit`，回傳檔說：
```
- 狀態: `in_review` （不變）
```
⇒ **「（不變）」證明它本來就已經是 in_review** —— **單子早就推進了。**

## 根因（`git_commit.py:255-261`）

```python
if r.returncode == 0 and "Success" in (r.stdout or ""):
    print(f"📋 TASK-{n} …讀單檔：AgentCommands/Tasks/tasks/{n:04d}.md")   # ← n 是 str
else:
    print("⚠ … 推進失敗，單子狀態沒動 …")
except Exception as e:
    print(f"⚠ TASK-{n} 推進失敗（{e}）—— 單子狀態沒動，需手動補。")
```

`n` 來自 `re.finditer(r"TASK-(\d+)")` ⇒ **是字串**，而 `{n:04d}` 對 str 會丟 TypeError。
⚠ 而那行在 **success 分支**裡 ⇒ **推進已經成功之後才炸**，
然後被外層 `except` 接住，印成「推進失敗」。

## 為什麼這隻比一般的 bug 貴

**三本帳同時錯，而且方向最壞：**

| 帳 | 真實 | 它說 |
|---|---|---|
| 處置 | ✅ 單子推進了 | ❌「推進失敗」 |
| 結果 | ✅ 狀態已是 in_review | ❌「**單子狀態沒動**」 |

📌 第二句最貴：它不只說錯，**它斷言了一個它不知道的事實**，
然後叫人去做一個**不需要的手動補**。而手動補如果有副作用（重複 sha、重複公告），
那個副作用是這句假話造成的。

⇒ 一般形：**`except` 只知道「這裡炸了」，它不知道「炸之前做完了什麼」。
   失敗處理不可以替它不知道的事作答。**


- [ ] `{n:04d}` 修好（`n` 轉 int，或改成不需要補零的寫法），success 分支不再丟例外
- [ ] **把「送出」與「回報」分開**：subprocess 的成敗判定完成後才做輸出，
      讓輸出的例外不可能被讀成推進失敗
- [ ] `except` 的措辭改成**不替結果作答**：不可以再出現「單子狀態沒動」這種斷言，
      要改成「這一步的**回報**出錯；單子可能已經推進，去讀單檔確認」
- [ ] 讀數 A：正常路徑跑一次帶 `Fixes TASK-n` 的 commit ⇒ 印出成功指路、**不丟例外**
- [ ] 讀數 B：**造一次輸出層例外**（或以 fixture 呼叫該分支）⇒ 訊息必須是「回報出錯」
      而不是「推進失敗／狀態沒動」
- [ ] 讀數 C：**真的送不出去**時（run_cmd 非零）⇒ 仍要印「推進失敗」，
      兩種失敗**不可同形**（這格是反向對照，只驗 B 的話會把兩者混成一句）
