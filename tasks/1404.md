## 任務描述

Tim 2026-11-28：等高線地形「地形資料來源轉等高線過程中會出現很多瑕疵&效能問題」⇒ 分析改用其他方式保存地形高度（儘量做到球表面積上資料平均）；之後追加：沒有接縫、精度可更高（10 GB 內）、分多檔保存、不用考慮城鎮風險（之後重新處理）、格式方便地形編輯器（遊戲內建工具可以調整並輸出）、高度範圍 −20000～20000 公尺（等高等深一起、含海溝）、地球儀渲染整個重做（實際模型、顏色照土質／植被／冰蓋）。

本單：做「一個驗證用的地球儀（新架構）然後填入台灣的資訊測試看看」，並分析「本體改用c# 嵌入網頁做UI的可行性」。試作，全部是新檔，不動現有的地形鏈、globe.html、城鎮。

## 留言

### 💬 #1 summit 2026-11-28T12:47:56.171Z
**判定：本體改 C#、UI 嵌網頁「做得到」，但不建議整個重寫；建議的形狀是「C# 核心當本機服務、畫面與 UI 留在網頁」，從要重做的世界層（高度格、尋路、經濟模擬）開始搬。**

憑據（現況，2026-11-28 wc -l）：
- 手寫的遊戲程式約 8.4 萬行 JS（Blockside src/js 51,720、Blocksail world/*.js 32,047）＋ HTML 約 7,200 行；工具 .cjs 194 支 31,809 行，其中 162 支用 vm 直接跑遊戲的 JS；C++ 約 1,540 行（編成 wasm）；兩個 repo 沒有任何 .cs
- 畫面：手寫 WebGL2、約 40 支以上 GLSL；UI 是 DOM 疊在畫布上；音效全是 Web Audio 合成
- 平台：Electron＋Steam（Windows 先）、手機 ＝ 瀏覽器直接開；macOS／Linux 先靠 Proton
- 決定論：同種子逐位元組相同、烘焙快取照程式檔指紋（ARCHITECTURE §1、NATIVE §5）
- NATIVE.md §1 當時選 C++ 不選 C#，理由是 C# 編成 wasm 要帶整套 .NET 執行環境 —— 這個理由對「瀏覽器、手機」那一側現在仍成立

三種「本體 C#」：
1. C# 核心（模擬、尋路、地形、存檔、讀大檔）＋網頁照舊負責畫面與 UI —— 建議。核心編成原生執行檔，由 Electron 帶起來、走本機連線（開發時就是 C# 版的 world_serve）；頁面不用分兩套。得到真的執行緒、struct（尋路一個節點 470 bytes ⇒ 21 bytes 那種問題）、型別、10 GB 高度格可以直接映射檔案。
2. 整個原生（畫面也用 C# 重寫）＋網頁 UI 疊在上面 —— 不建議。透明網頁疊在原生畫面上每個平台各一套做法（Windows 是 WebView2 的合成模式或離屏 Chromium），而畫面不是現在的瓶頸；瀏覽器版、手機瀏覽器直接開會整個不見。
3. 維持現狀、重的計算繼續 C++ ⇒ wasm —— 最省，但改不了 8 萬行 JS 的型別與記憶體問題。

風險：
- 手機單機：C# 核心在瀏覽器裡只能編成 wasm（要帶執行環境、速度我沒量），不然手機就得連到一台跑核心的機器，或另外出原生 App。這是產品決定。
- Proton：WebView2 在 Proton 底下不可靠 ⇒ 殼留 Electron（自帶 Chromium），不要換成 C# 視窗＋WebView2。
- 決定論：C# 的 Math.Sin／Pow 各平台不保證同一個位元 ⇒ 一樣要自己帶 fdlibm；Math.Round 是四捨六入五成雙、字典的順序、數字轉字串都跟 JS 不同，要逐條規定。
- 工具：162 支 node 工具要改成呼叫 C# 核心或跟著搬。

沒量的：C# 核心比 JS 快多少（原生、wasm 各一個數）、每一格畫面跨程序傳資料的成本。
建議先量：把這張單寫的高度格編解碼＋查一點（約 250 行、有逐位元組的對拍）搬成 C#，量原生與 wasm 各跑多快，再決定。

球在 Tim：要不要做這個 C# 小試作、手機單機要不要保留。

### 💬 #2 summit 2026-11-28T12:51:11.092Z
**更正上一則的範圍**：Tim 之後說「不一定要用c#」「之後的規劃是遊戲發行會打包成exe」「c++ rust都可以一起分析」⇒ 語言不限，三種一起比。

判定（沒有在這個專案實測，下面是一般的性質＋本專案已有的讀數）：
- 殼先留 Electron（現在就是 exe，自帶 Chromium）；核心（模擬、尋路、地形、高度格）從 JS 搬出去。
- 核心的語言：首選 Rust（速度同 C++、編譯器擋記憶體錯與執行緒搶資料、同一份可以編成原生模組與瀏覽器用的 wasm）；Tim 自己要讀、要改程式，或要沿用 Senate 那一套 ⇒ C#（代價：瀏覽器那一側要另外處理、數值迴圈一般慢一截）；C++ 留在已經寫好的約 1,540 行，不擴大（記憶體錯不會報錯，一群 agent 同時寫最危險）。
- 畫面（Blockside 手寫 WebGL2 約 5.2 萬行）先不動。

憑據：NATIVE.md 的讀數（A* JS 104.9 s／3.1 GB ⇒ C++ 43.4 s／1.5 GB；地形第 3 步 2.1×、整塊 1.2×；布料 wasm 只快 15～20%）⇒ 原生對數值迴圈是 1.2～2.5 倍，三種原生語言之間的差距比這個小。
這台的工具：.NET 10.0.401、emsdk 的 clang、VS 2022 有；Rust 沒裝。

球在 Tim：要不要做「同一個模組（高度格解碼＋查一點）三種語言各寫一份」的對照試作（要同意安裝 Rust）。
