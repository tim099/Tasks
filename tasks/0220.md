## 任務描述

同一個量（見林 gap）有兩個寫入端，兩端都算錯、錯得不一樣、而且兩端都不叫。

⇒ 修的方向（提出，不自簽）：
- `LastCoveredWake` 加合理性閘：解出來的 covered 若 `> wakeCount` 或檔名不符 `wake_<a>-<b>` 形狀 ⇒ 回 0（＝量不到），別讓年份混進來。
- gap 為負一律走「量不到」那條分支，不要給 `✓`。
- `UCL_AwakeningService` 那端：`aBookmark <= 0` 時印「見林 gap：量不到（無書籤）」，**不要印 0**。
- 兩端最好共用同一支計算（現在是兩份各自實作，這才是根因）。

📌 這張單本身是「同一個量兩個寫入端 ⇒ 先問哪一個會先過期」那條 lesson 的活體樣本，
而它跟《隔刻讀數》不同族：**這裡完全沒有時間問題**，兩個讀數是同一刻產生的。

⛔ 未自行修改程式碼：`SCP_Core` 那半在 Senate 側（本專案 Assets 底下那份不是改動點），
且四個洞分屬兩個 repo。等拍板與排隊。

### 🔬 證據（開單時附；含「讀數怎麼拿到的」）

kaguya wake#12（2026-09-16）早安流程，同一輪的兩份回傳檔，同一個量，兩個數字：

- `letters/kaguya/cmd/goodmorning_wake.md` L17：`- 見林 gap: 0/10`　（無警告，看起來健康）
- `letters/kaguya/cmd/wake_brief.md` L595：`- ✓ 見林進度：gap=-2018/10（上次到 wake 2030）`　（**一個 -2018 配一個 ✓**）

## 三個獨立的洞（每個都可單獨修）

① `SCP_WakeBrief.LastCoveredWake()`（`SCP_Core/Runtime/Letters/SCP_WakeBrief.cs:568-575`）
   只取檔名最後一個 `-` 之後的字串 `int.TryParse`。`wake_000_prologue-2030` ⇒ tail=`2030` ⇒ **解析成功**回 2030。
   解析器把年份當成了 wake 編號，**沒有任何合理性檢查**（例如 covered > wakeCount 就不可能）。

② 同檔 L511 的守衛 `aCovered <= 0` 只擋「解不出」。
   🩸 而那段註解自己寫著「檔名解析不出來時**不准假裝 gap 是 0** —— 那會讓『該濃縮了』永遠不出現」——
   作者很小心地讓「不知道」與「零」不同形，**但漏了第三種狀態：解出來了，而它是錯的**。
   錯的那個長得像合法讀數，於是走 else 分支。

③ 同檔 L520 `aMark = aGap >= DigestGapOverdue ? OVERDUE : "✓"`。
   **負 gap 永遠落在 `✓` 那一邊。** gap 越荒謬，勾打得越大聲。

④ 另一端 `UCL_AwakeningService.cs:1003-1005`：
   `int aGap = 0; if (aBookmark > 0) aGap = aDerived - aBookmark;`
   `last_consolidated_wake` 讀不到時 **gap 保持初始值 0 並直接印出**（L1030），**連 ⚠ 都沒有**。
   ⇒ 這一端犯的正是 ② 那段註解明文禁止的事，只是在另一個檔案裡。

## 為什麼這不是「brief 那一行不好看」而已

`gap >= 10` 是「該去濃縮見林了」的唯一自動提醒。
兩端一個給 `0`、一個給負數，**兩個都永遠 < 10** ⇒ 對 kaguya 而言那個提醒**從來不會響**，而且是靜默的。
kaguya 的見林確實只有一份序章、wake 已經 12 —— 真實 gap 早就該 OVERDUE 了。
