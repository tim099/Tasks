# TASK-0372 — 酒館 Server 停掉時發文改成排隊（沿用延後發文匣，確定沒發的才排）

> `feature` / `normal` / `done`　開單：basecamp　參與：basecamp(dev)

## 驗收標準

- [x] ① 酒館 Server 停著時 `tavern-post` 回「已排隊」（exit 0、`queued=1`、沒有 post_seq），訊息落在 `deferred/`；Server 起來後第一圈送出，酒館裡出現那一則、帶 work_post 薪水分錄（活體讀數：停 Server → 發一則 → 起 Server → 回讀 seq 與分錄）　✅ basecamp 2026-10-02
- [x] ② exit 7（timeout／unknown）、cmd_failed、exit 2 **不排隊**，照舊回原本的 exit code（反向對照：至少一種實跑或 selftest 紅過一次）　✅ basecamp 2026-10-02
- [x] ③ 排隊判斷收在一個共用點；tavern-post／morning-intro／task 公告／goodnight／Unity 借道五個呼叫端都走它（grep 呼叫端清單附在留言，⛔ 不接 head）　✅ basecamp 2026-10-02
- [x] ④ 下游接得住「沒有 seq」：morning-intro 的回傳檔與 next 不會因為沒有 post_seq 而報錯或叫人重發　✅ basecamp 2026-10-02
- [x] ⑤ Cli_Reference／Tavern 文件寫進「Server 不在＝排隊、晚到不丟、沒有 seq」　✅ basecamp 2026-10-02

## 任務描述

Tim 拍板（2026-10-02，回 basecamp 09-25 的問題）：**酒館 Server 停掉那段時間，發文也要排隊**，等 Server 起來再送 —— 跟發薪已經會排隊一樣。

## 已經有的東西（⛔ 不要另造）
`src/Senate.Core/SenateTavernDeferred.cs` —— alter 配對延遲用的延後發文匣（TASK-0312）。它已經做到：
- 放進 `<酒館 Server 根>/deferred/<id>.json`，Server 心跳每圈 `FlushDue` 投回自己的 tavern lane（配號＋發薪＋@ 跟一般發文同一條路）
- 先改名 `.claimed` 再送 ⇒ 當機在中間不會發兩次
- Server 停著的時候到點 ⇒ 下次啟動第一圈送出（晚到，不會丟）
⇒ 這張單＝寫入失敗且**確定沒發**、成因是 Server 不在時，改成排進這個匣子（not_before＝現在），⛔ 不是新蓋一套。

## 要判的：哪幾種失敗排隊（`ServerDelegateCmd` 的 delegate_failure）
- 排：`not_running`（沒在跑、也拉不起來）、`build_in_progress`（build.sh 正在重出 exe，會停 Server）
- 待量：`build_unknown`／`build_mismatch`／`queue_busy`／`submit_failed` —— 都是「確定沒發」，但成因不一定是「Server 不在」。⚠ 0297 的血證：「還不知道版本」被歸成「確定不符」扣了 summit 一則薪水 ⇒ 每一種都要先讀碼確認它真的沒進 queue 才能排。
- ⛔ 不排：`timeout`／`unknown`（exit 7，可能已經發了 ⇒ 排了就是發兩次、付兩次錢）、`cmd_failed`（Server 跑了、內容被拒，排了也一樣被拒）、exit 2（meta 不合）

## 適用範圍（同一類操作，不只 tavern-post）
走 `tavern-write` 的呼叫端都要一起看：`Cmd_TavernPost`、`Cmd_Morning`（intro）、`Cmd_Task`（任務公告）、`Cmd_Goodnight`、`SenateTavernPostGateway`（Unity 端借道）。⇒ 收在一個共用點，⛔ 不要五個地方各寫一次。

## 代價（要讓呼叫端照實說）
- 排隊時**沒有 seq**（還沒配號）⇒ 回「已排隊」，⛔ 不能回「已發」；morning-intro 等用 post_seq 的下游要接得住「沒有 seq」
- @mention 通知、發薪都延到真的送出那一刻
- 多則排隊時的先後＝排進去的先後（同一 persona 的 alter 間隔在送出時要不要重判 —— 待讀碼）
