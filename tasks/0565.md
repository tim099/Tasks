## 是什麼
`SCP_Core/Runtime/Process/SCP_ServerCmdClient.cs` 的私有 `WriteAtomic`（:256–270）寫 Server 的 queue.json 用的是：
`File.WriteAllText(tmp)` → `if (File.Exists(iPath)) File.Delete(iPath)` → `File.Move(tmp, iPath)`，IOException 重試 5 次。
這是 `Coding_Standards.md §1.1` 點名不准的「先 Delete 再 Move」：兩步之間有一格**檔案不存在**。

## 射程（⚠ 照量到的寫 —— 比我在 SCP_Core 474dda2 提交訊息與 TASK-0533 #4 留言裡寫的小）
那兩處我寫「Server 的 LoadQueue 讀到不存在時回空骨架」，暗示 Server 會讀進那一格。**沒量就說了**。讀碼的結果：
- 客戶端寫（:127 `SCP_FileLock.Acquire(aQueuePath)` 包住讀改寫，:150 才 WriteAtomic）與 Server 讀（`ServerExecutor.cs:149`、:364 都在同一把 `SCP_FileLock` 裡）**拿同一把鎖** ⇒ 守這把鎖的讀者看不到那一格（:233 的註解寫的就是這個前提）。
- 剩下的風險是兩種，⛔ 都還沒量：
  1. **行程死在 Delete 與 Move 之間**（被殺、斷電、build.sh 收掉 Server）⇒ queue.json 不見、資料留在 `.tmp.<6碼>`。下一個 LoadQueue 讀到「不存在」⇒ 回空骨架，之後的寫入把它寫成一份只有新指令的 queue ⇒ 排在裡面的指令沒了，而沒有任何一層會叫。
  2. **沒拿鎖的讀者**：例如 `AgentCmdClient`（Senate.Core）的唯讀輪詢讀到 Missing 就當成空的 Commands（:400 附近）。它讀的是不是同一個檔、還有沒有別的讀者，要開工的人去列。

## 要做的
1. 讀數先行：列出所有讀這個 queue.json 的地方，各自有沒有拿鎖；寫淨室測試重現「死在中間」那一格（舊寫法在 Delete 後、Move 前中斷 ⇒ 檔案不存在、tmp 還在）當反向對照。
2. 換成 `SCP.Core.Io.SCP_SharedFile.Replace`（目標存在走 File.Replace、不存在走 Move，共享衝突有上限地重試）—— TASK-0533／0534 收成一支的那個。保留多個寫入端（同一把鎖）的行為。
3. 照流程：認領帶 scope、`senate cmd commit` 單層；SCP_Core 的提交 agent 自己 push；Senate 的 SCP_Core 指標 bump 要 Tim 明說。
