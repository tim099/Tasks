# TASK-0009 — 主 Task／父子關係做成一等公民（epic_id 生效、subtask 有寫入端、tag 可篩、claim 不該改狀態）

> `feature` / `high` / `done`　開單：basecamp　參與：basecamp(pm)、summit(dev)、basecamp(qa)

## 驗收標準

- [ ] `epic_id`（或改名 parent）**有讀取端**：至少 list 能按它篩、show 能列出子項與「還剩幾格沒關」
- [ ] `subtask_indices` 有寫入端（op=link 加一種 op_link=subtask_of / has_subtask，雙向寫入同 blocked_by 的先例）
- [ ] `tags` 可篩：`op=list --arg tag=epic` 能撈出所有主 Task（現在寫得進去但沒有任何查詢端）
- [ ] `op=claim` 不再無條件把狀態設成 in_progress —— **只有 dev 開工才是 in_progress**
- [ ] 上面每一格都要有實跑讀數，不是「欄位存在」

## 任務描述

PM（basecamp）2026-08-24 開單。動機是 Tim 問「主 Task 機制是不是已經有了」，而量出來的答案是**半個**：

| 能力 | 現況（讀 code 得來，不是猜） |
|---|---|
| 任務互相關聯 | ✅ 活的 —— `op=link blocked_by/blocks/related_to`，雙向寫入，且 blocker 閘真的會擋 commit 推進 |
| 父子（主 Task ↔ 細項） | ⛔ **不生效** —— `epic_id` 只有寫入端（create），`UCL_TaskIO.cs:36` 作者自己註明「目前沒有任何讀取端」 |
| 子項清單 | ⛔ **連寫入端都沒有** —— `subtask_indices` 只有序列化與解析，沒有任何 op 會寫它 |
| tag 標記主 Task | ⚠ 半個 —— create 寫得進 `tags`，但 `op=list` **沒有 tag 篩選**⇒ 寫得進去、查不出來 |

⚠ 這批「欄位在、沒人讀」的形狀就是我見根第三名那條：**存在 ≠ 生效**。
而原作者是刻意的（註解寫「要開始用 Epic 的那天再建，而那天會有一個真的 Epic 當第一顆探針」）——
TASK-0008 就是那顆探針，所以現在是那一天。

⛔ 一格 PM 判斷：`claim` 那條**先修**，它會咬人 —— 我今天接 PM 時差點用 claim，
那會把 TASK-0001 從 in_review 倒退回 in_progress，把剛驗完的 QA 狀態清掉，而它不報錯。
（我改走 assign 才避開，並且逐格對帳五張單的狀態沒有被我動到。）

## 結單說明

QA 過：五條全部實跑（epic 篩+show 列子項與未關數／subtask 雙向兩邊 frontmatter 回讀／tag=epic 撈出主 Task 且 status=all 也吃／claim 不再無條件推／②的首筆讀數是真實使用中順手拿到的）。⚠ 驗收過程中發現我自己造的雙清單問題（related_to 傘 vs subtask_indices），已當場遷移並宣告 subtask_indices 為子項唯一真相源。另撈到 op=link 能連不能斷的缺口，不擋本單。
