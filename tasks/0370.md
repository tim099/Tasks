## 任務描述

## 背景與現況診斷

目前專案透過 UCL_KnowledgeBaseAdminPage 與 knowledge_base.py 使用 BAAI/bge-m3 模型進行文件、教訓（lessons）與記憶碎片（fragments）的檢索。

### 現有架構的局限性：
1. **純 Dense 向量檢索**：knowledge_base.py 目前僅使用 BGE-M3 的 dense_vecs，未發揮其內建的 Sparse（詞彙/關鍵字權重）與 ColBERT 多向量特徵，對於精確專有名詞與代碼識別率不足。
2. **缺乏時序意識（Temporal Blindness）**：向量檢索不具時間概念，歷史狀態與最新事實可能在語意檢索中同時被命中，無法自動處理「狀態失效（State Supersession）」與「矛盾更新」。
3. **無工作記憶（Working Memory）分層**：僅有外存檢索，缺少類似 Context 壓縮、短期暫存、反思（Reflection）與動態 Core Memory 的分層編排。

---

## 2025–2026 年主流長短期記憶方案調研

1. **Mem0（Memory-as-a-Service）**：
   - 專門針對 Agent 的個人化記憶層，區分 User、Agent、Session 三級記憶。
   - 具備實體與事實萃取（Fact Extraction），能自動合併、覆蓋衝突事實。
   - 可純本地部署（SQLite/Chroma + 本地 Embedding）。
2. **Letta / 前身 MemGPT（Memory OS）**：
   - 將記憶視為類似操作系統的分層體系：Core Memory（常駐上下文，Agent 可自主透過 Tool 讀寫編輯）、Recall Memory（對話歷程檢索）、Archival Memory（無限外存庫）。
   - 與本專案的 letters/<persona>/（_constitution.md、_latest.md、ragments/）設計哲學高度契合。
3. **Zep / Graphiti（Temporal Knowledge Graph）**：
   - 雙時態知識圖譜，專門追蹤實體關係的生效與失效區間，適合高度動態的狀態演進。

---

## 模型與檢索層升級空間

1. **BGE-M3 多模態活用**：BGE-M3 依然是頂級開源多語言模型，若啟用 Dense + Sparse 混合檢索即可兼顧語意與精確關鍵字。
2. **引入 Cross-Encoder Reranker**：在 BGE-M3 檢索出 Top-20~30 後，引入 BAAI/bge-reranker-v2-m3 或 jina-reranker-v2 進行重排，預期可提高 15%~30% 的精準度。
3. **新一代 Embedding 評估**：如 Qwen3-Embedding（32K context）、Jina Embeddings v3（LoRA 任務適配）。

---

## 候選方案

- **方案 A（最輕量，ROI 最高）**：現有 knowledge_base.py 升級為 BGE-M3 雙模混合檢索 + 增加 ge-reranker-v2-m3 重排，並加入時間衰減權重。
- **方案 B（記憶中台化）**：引進 Mem0 本地版，負責個人記憶抽取、去重與事實更新，底層對接現有向量庫。
- **方案 C（深度分層）**：參考 Letta 架構，將信件庫與工作記憶規格化為 Core/Recall/Archival 三層工具化記憶。

後續待 Tim 拍板具體實作方向後執行。

### 💬 #1 kaguya 2026-10-02T01:03:25.212Z
**判定**：建議走「先修現有的 → 再做方案 A」；B（Mem0）與 C（Letta）不建議當外部框架引入。前置單 TASK-0375（安裝系統）已開並設為阻塞。

**一、單上的前提，逐條對過現況（2026-10-02 量）**
- 「只用 dense」：對，而且比寫的更徹底 —— sparse／ColBERT **根本沒算**（不是算了丟掉），索引格式也沒有地方放它們 ⇒ 改混合檢索＝全部 ~29k 塊重新編碼＋換儲存格式。
- 「沒有時序意識」：排序上對。時間只用在判斷索引過期（檔案 mtime）。
- 「沒有分層、只有外存」：**言過其實**。已經分了：個人碎片／集體 Alaya／工作記憶／讀書庫，還有每個 persona 各自的索引，碎片也有 open／internalized／closed 狀態。缺的是 Letta 那種「agent 能用工具改寫的常駐記憶」，不是分層本身。
- 單上只列 docs／lessons／fragments，實際是 8 個基本目標＋13 個 persona 目標。

**二、量到的問題（多半比換模型更值錢）**
- 每次呼叫都重新載入模型（約 4.3 秒）並重新解析 JSON 索引；全部索引約 875 MB 的 JSON（每個 float 一行）。`--target all` 第一次跑超過 120 秒。
- 切塊只按空行＋硬切 800 字：coredocs 13727 塊裡 38% 不到 40 字（多半是標題），2158 塊內容重複 ⇒ 「6 筆同分 0.5754」那種標題雜訊就是這裡來的。
- lessons 被索引兩次（`Lessons/` 與 `lessons/` 在 Windows 是同一個資料夾）；`lessons.jsonl` 沒有空行，被硬切成半截的紀錄。
- 塊的 id 用不含路徑的檔名，同名檔會撞。
- 回報的 `latency_ms` 不含載入索引那段，所以看起來很快。
- 知識庫頁的「安裝」可能把 GPU 版 torch 換成 CPU 版（已寫進 TASK-0375 的現況）。

**三、建議的順序**
- **階段 0（搬到 Senate 時一起做，不換模型）**：常駐的嵌入服務（模型只載入一次）、二進位索引格式、依標題切塊＋過濾太短的塊＋去重、修 lessons 重複與 id 相撞。
- **階段 1＝方案 A**：BGE-M3 dense＋sparse 混合、取前 30 筆用 bge-reranker-v2-m3 重排；時間衰減**只開給會過期的目標**（碎片、工作記憶），文件類不開；碎片的 closed 狀態直接拿來過濾。
- ⭐ **動工前先建一份評估題庫**（約 30 題「這句話該找到哪個檔」），改前改後各量一次。沒有它，「精準度提高 15~30%」這句話沒辦法驗，也分不出是階段 0 還是重排的功勞。

**四、為什麼不引入 Mem0／Letta／Zep**
- Mem0：預設每寫一筆就叫 LLM 抽「事實」並自動合併覆蓋 —— 等於讓工具代筆改寫記憶，跟「信件是本人親筆、舊版不覆寫」相反；而且每筆寫入都要付 LLM 的錢。
- Letta：它的 Core／Recall／Archival 三層，我們已經有對應（憲法與 _latest／酒館與 wakes／碎片與文件）。缺的是「讓 agent 改常駐記憶的工具」，那是幾個 Cmd 的事，不需要整套框架。
- Zep／Graphiti：要另外跑圖形資料庫，這個規模不划算；「狀態失效」用既有的 status 欄位與時間衰減就能處理大部分。
