# TASK-0098 — wake_brief.py 見樹排序把「最新一封」指錯 —— 混格式 written_at 的字串排序（C# 那側已修）

> `bug` / `wrong` / `normal` / `done`　開單：basecamp　參與：calli(dev)

## 驗收標準

## 現場（basecamp 的信件庫，2026-09-01）

同一個目錄裡兩種 `written_at` 格式並存：
- `wakes/000082_20260901T091259Z.md` ⇒ `written_at: 2026-09-01T09:12:59.759Z`（帶連字號）
- `20260831T101830Z_wake81_letter_to_future_self.md` ⇒ 緊湊 ISO

`wake_brief.py` 的見樹合併把它們拿**原字串**排序 ⇒ `-`(0x2D) < `0`(0x30)
⇒ 帶連字號那種一律排前面 ⇒ **最後印出的那封（標「最新一封」）變成 08-31**。

## 讀數（開單人填，非推理）

1. 今天早上 python 產的 brief（1314 行）：`### 📅 2026-08-31（最新一封）`，
   而 09-01 那封被排成「往前補」。
2. 同一個目錄的 `_latest.md` 檔頭：`written_at: 2026-09-01T09:12:59.759Z`
   ⇒ **指標說 09-01，見樹的排序說 08-31，兩個視圖在同一份 brief 裡互相打臉，沒有一格會紅。**
3. C# 那側同一隻已修（`2d9ca29`，`NormalizeStamp` 只留數字再比），修後印
   `### 📅 2026-09-01（最新一封）` ⇒ 與 `_latest.md` 一致。

## 射程 / 為什麼還要修

生產端 2026-09-01 已翻成 C#（TASK-0097），所以**正常早安路徑不再走 python**。
但 `awakening.py brief` 仍是「Editor 未開」的備援 ⇒ 那條路上這隻還活著，
而它的症狀是「日期看起來很正常、只是順序反了」。


- [ ] ① 重現讀數：在混格式的信件庫上跑 `awakening.py brief`，記下「最新一封」指到哪一封
      （現況：08-31；期望：09-01）
- [ ] ② 修正落盤：排序鍵正規化（只留數字再比，或轉成同一種格式再比）——
      ⛔ 不要改成「只吃帶連字號那種」：緊湊格式是活的現況，那樣會把它整批當成解析失敗
- [ ] ③ 異源複驗：同一個 persona 同一時刻，`awakening.py brief` 與
      `senate cmd wake-brief` 的「最新一封」指到**同一封**（兩個獨立實作對同一份資料）
- [ ] ④ 反向對照：全部同格式的信件庫（例如 Template）修前修後順序不變 ——
