# TASK-0120 — 觀影 step=cycle 期間 Editor 進入 busy 數分鐘 —— 觸發條件是「剛開錄影就開場」（水位不足每輪等滿）

> `bug` / `blocking` / `high` / `todo`　開單：summit　⚠ **尚無參與者**（沒有人在做這件事）

## 驗收標準

## ① 重現讀數（開單人已填，見 evidence）

- [x] 觀影 `step=cycle` 期間 Editor 進入 Unity 的 busy 對話框，callstack 指名
      `UCL_AgentCommandWatcher.OnEditorUpdate` ＋「Waiting for user code in UCL_Core.dll to finish executing」，
      **busy 01:31**（Tim 螢幕，第三方讀數）
- [x] **觸發條件量出來了**：感官水位不足時每輪等滿上限（回傳檔自印「等水位 30s 仍不足」＋「目標間隔 45s」）；
      水位追上之後同一支 cycle 的「本輪實等」掉到 **25s** ⇒ **凍多久 ≈ 那一輪等多久**
- [ ] 反向對照（**必做**）：水位充足時連跑 3 輪 cycle ⇒ Editor 不該出現 busy 對話框。
      只驗「會凍」的話，一個永遠凍的東西也會通過
- [ ] 量一個數字：`OnEditorUpdate` 的 busy 時長 vs 該輪回傳檔的「本輪實等 + 等水位」——
      兩者比例是判斷「是不是就是那個等待」的唯一硬證據

## ⛔ 已排除的嫌疑犯（不要去修沒壞的地方）

- [x] **montage 外部行程不是原因** —— `Cmd_StreamWatch.RunMontageAsync`（約 2589 行）
      確實把 `StandardOutput.ReadToEnd` ＋ `WaitForExit(60000)` 包在
      `await System.Threading.Tasks.Task.Run(...)` 裡，檔頭第 11 行那條硬規則
      （「縮圖牆是外部 process，一律 await Task.Run 包起來，不得在主執行緒輪詢 WaitForExit」）**有被遵守**。
      ⇒ 這一格我讀過 code 才寫，不是推論。**修錯地方的成本比慢一天高。**

## ② 待判的成因（開單人不下定論）

- [ ] 節奏等待是**牆鐘迴圈**：`while (DateTime.Now < aSlot) { … await UniTask.Delay(500, DelayType.Realtime) }`
      （約 1243-1247 行；1408 行另有 `UniTask.Delay(1000, Realtime)`）。
      ⇒ 要判的是：**Editor 模式下這條 async 鏈存活數分鐘時，Unity 會不會把它算成「user code 還沒結束」**
      而進入 busy／擋住 domain reload。（await 本身不佔 CPU，但 Unity 的 busy 判定不一定看 CPU。）
- [ ] 若成立，方向是**把等待搬出 Cmd 的執行期**（例如：cycle 立即回「還沒到格線」讓呼叫端稍後再來），
      而不是把 delay 改短 —— 改短只是讓凍的次數變多。
      ⚠ 而這條跟 skill 現行的「**等待由本 Cmd 執行，呼叫端不必也不要自己等**」直接衝突
      ⇒ 這是設計取捨，要 Tim 拍板，不是實作細節

## ③ 異源複驗

- [ ] 修完之後由**另一位** persona 在「剛開錄影」的條件下開場連跑 3 輪，
      Tim 端確認沒有 busy 對話框（**開單人的讀數不算證言 —— 我是肇因**）
- [ ] 同時確認沒有降級：cycle 仍然只在水位夠時給素材（不可為了不凍而端未辨識完的段落）

## 📌 為什麼這值一張單，而且是 blocking 形狀

它不是「慢」—— 它讓 **Tim 的 Editor 在觀影期間反覆不可用數分鐘**，而觀影是**多人同時**的活動
（今天四位陪同者），每個人的 cycle 都會各佔一次。
⚠ 而它平常不現形：正常場次水位早就追上、等待接近 0。**「剛開錄影就開場」是它的觸發條件** ——
於是它專門咬「第一次開這部片」的那一場，也就是**每一部新片的第一場**。

## ⛔ 我排除掉的那個嫌疑犯（讀 code，不是推論）

`Cmd_StreamWatch.RunMontageAsync`（約 2589 行）：

```csharp
bool aExited = await System.Threading.Tasks.Task.Run(() =>
{
    aOut = aProc.StandardOutput.ReadToEnd();
    aErr = aProc.StandardError.ReadToEnd();
    return aProc.WaitForExit(60000);
}, iToken);
```

檔頭第 11 行的硬規則（「縮圖牆是外部 process，**一律 await Task.Run 包起來**，
不得在主執行緒輪詢 WaitForExit」）**有被遵守** ⇒ 縮圖牆不是原因。
📌 同檔 2516 行還留著一條註解點名別的實作（`UCL_BartenderDaemon.RunBalanceQuery`）
「內部 while+WaitForExit 是主執行緒輪詢」—— 那條**不是**本 cycle 走的路。

## 🩸 而開單人自己在這件事上高報過一次，一起記著

我一度對 Tim 說「回傳檔檔頭是起跑時刻 ⇒ 那一輪佔住 Editor 約 3 分 56 秒」。
**那是錯的**：queue 檔顯示那筆當時 `RunCount=0`（沒開始跑）⇒ 檔頭那個時間是**派遣時刻**，
3 分 56 秒是它**排隊**的時間。⇒ 我在沒有去量「檔頭是哪個時刻」的情況下，
描述了一個東西的射程（憲法⑤）。真正可信的凍結時長只有 Tim 螢幕上那個 **01:31**。
