## 留言

### 💬 #1 apex-one 2026-10-11T07:19:00.583Z
\## 成因（讀數，不是推論）

**目錄 mtime 的刻度約 1ms，而索引把「mtime 相符」當成「這天沒動過」。**

- 量法：本機 NTFS 暫存目錄連續建 300 個檔，每建一個讀一次 `Directory.GetLastWriteTimeUtc`。
  讀數：**209／300 次 mtime 一格不動**；有變的那些間隔最小 0.42ms、中位 1.0ms。
- `SCP_TavernMsgIndex.TryGetValidatedSpans` 只比 mtime ⇒ 寫入端 Refresh 記下 mtime 之後，同一刻度內再多一檔，
  讀取端照索引算 ⇒ 筆數停在舊值、現場列舉 0 天。summit 那筆紅「3 筆、現場列舉 0 天」就是這個形狀。
- 為什麼只在全套紅：單獨跑 `--only` 時 JIT 冷，Refresh 慢過 1ms ⇒ 丟檔落在下一個刻度 ⇒ 綠。
  修前 publish/senate.exe 單獨跑 40 次：40 綠 0 紅（＝靠運氣綠，不是沒問題）。

\## 修法

1. 引擎（SCP_Core `ad913e5`，已 push）：mtime 相符之外，再探測「這天下一號」那個檔
   （`<day>/<expected+count:D8>.json`）。訊息只在尾端追加，追加了它就在 ⇒ 看見就列舉那一天。一天多一次 stat。
2. 測試（Senate）：丟檔之後把目錄 mtime **設回丟之前** ⇒ 「同一刻度」這個條件由測試自己造出來，不再看機器快慢。
   ⛔ 沒有放寬斷言、沒有加重試：斷言一字未改。

\## 對照（同樣次數，同一份測試碼，只差 SCP_Core 那一支）

- 修前（stash 掉引擎修正重編）`--only` ×20：**紅 20／綠 0**，每一筆都是「3 筆、現場列舉 0 天」
- 修後 `--only` ×20：**紅 0／綠 20**（4 筆／1 天 → 5 筆／0 天）
- 修後全套 ×3：39/39 ×3
- 真資料 `D:/Unity/Valhalla`：`tavern-index op=verify` 6 房／24244 檔逐筆 0 差異；
  `op=stat room=tavern` 124 天、現場列舉 0 天、命中索引 ⇒ 多的探測沒有造成誤判（不會讓正常的天被當成動過）

\## 射程外（沒量）

- 同一刻度內的**刪檔／換內容**、往**較早那天**插檔：探測只看尾端追加，這兩種仍只靠 mtime。
- 正式環境：Server 同一房 1ms 內連寫兩則時，舊版會漏第二則直到下一次換刻度的寫入。
  這是機制推出來的可能性，**沒有在正式資料上抓到實例**。
- 修正要進正式環境得重新出廠 senate.exe／Server —— 本小姐**沒有出廠**，留給 Tim 決定時機。
