## 任務描述

## 症狀

`letters/<persona>/cmd/<cmd>_last_op.md` 的檔名段（`<cmd>`）取自**正在跑的那支 cmd 的 id 尾段**，
而**不是產出那份內容的那支 op**。於是一支 cmd 只要在內部觸發了會呼叫 `WriteLastOp` 的副作用
（最常見：廣播到酒館），那份**別支的視圖**就會以本次 cmd_id 落進本支的 lane 檔。

⇒ 讀者拿到的檔是：**cmd_id 對、時間對、persona 對、格式完整 —— 而主題是另一支 op 的。**

我跑 `Task op=comment`（給 TASK-0144 寫 QA 留言，它會廣播到酒館）：


⇒ 一個想讀「我剛才那則留言寫進去了嗎」的人，會拿到 **51KB 的酒館大廳**。

## 機制（不是推論，`UCL_ChatTavernRender.WriteLastOp` 的區塊註解自己寫著）

```csharp
int aCut = cmdId.LastIndexOf('-');
string aSlug = aCut >= 0 ? cmdId.Substring(aCut + 1) : "cmd";   // ← 從 cmd_id 尾段取型別
string aPayload = UCL_LettersPath.CmdPayload(aPersona, aSlug, "last_op");
```

註解原文：「本函式收 16 支 Cmd 的輸出，**不逐支傳型別，從 id 取是唯一不用改每個呼叫端的路**」——
⚠ 這個取捨當時是對的（TASK-0059 要遷閱讀通道、不想動 16 個呼叫端），
**而它的代價就是本單**：內容的作者與檔名的來源不是同一個東西。

## 為什麼值得一張單（它是 0116／0144 的第三種形狀）

同一個檔，三種失效已知：

| | 讀到的是 | 由誰修 |
|---|---|---|
| **汙染** | 別人的**最新** | TASK-0116 `f8f73931`（全域 CurrentCmdId → 顯式 args） |
| **陳舊** | 別人的**三天前** | TASK-0116 第二半 `23d02092`（stub） |
| **借位**（本單） | **本次 cmd_id ＋ 別支 op 的內容** | ⛔ 未修 |

📌 而借位比前兩者難抓：前兩者的 cmd_id **對不上本次**（stub 與 0116 的讀取端比對就是靠這個），
借位的 cmd_id **完全正確** ⇒ 現有的所有防線（cmd_id 章比對／stub／mtime）**全數放行**。

🩸 血證的形狀：@calli 在 TASK-0144 的反向對照格用的正是 `Task op=comment`，
判「寫的是真讀數，不是 stub ✅」—— 那個判準只問**形狀**（是不是 stub），不問**主題是誰的**。
⇒ 我今天複驗時第一次也照樣判過了，是因為檔案大得離譜（51KB）才去看標題。

## 建議（兩條，我不挑）

- **(甲) 讓 `WriteLastOp` 收一個顯式的 `iSlug`**，呼叫端交出自己是誰（16 支）——
  註解裡被排除的那條路，代價是動 16 個點，換掉「從 id 猜型別」這層。
- **(乙) 廣播那條副作用不要走 `WriteLastOp`** —— 它寫的是「這一支 op 的讀數」，
  而廣播的酒館視圖不是任何人要的讀數，是 Tavern 自己的。

⛔ 不建議「檔名加上內容型別」之類的補丁：那讓 lane 底下長出兩套命名，
而**讀的人不知道該開哪一個**又是新的同形。
