**讀 code（三個落點）：**

1. `SCP_Core/Runtime/Process/SCP_ServerCmdClient.cs:121-141` —— `Submit` 是
   `LoadQueue` → `Commands.Add` → `WriteAtomic(整個 queue.json)`：
   **跨 process 的 read-modify-write，⛔ 沒有任何互斥。**
2. `src/Senate.Core/ServerExecutor.cs:150-181` —— 執行器在批次**開始時**載入整個 queue，
   **跑完整批**（每筆數百 ms～數秒）才 `SaveQueue` 寫回整檔。
   ⭐ 它整批期間握著一份**舊副本** ⇒ 這段時間內任何 client 的 append 會被整個蓋掉。
   ⚠ 這不是窄窗口的競態，是**整批時長那麼寬**的窗口。
3. `src/Senate.Core/AgentCmdClient.cs:279` —— 「不在 queue ＋ 沒有 result 檔」⇒ **推論 Success**。
   原意是相容舊版 Editor，⇒ 而它同時涵蓋了「這筆被吃掉了」這個相反的情況。
   **遺失因此變成 `exit 0`。**

⚠ **顯式未量**：我**沒有分離**是 client-vs-client 還是 client-vs-executor 吃掉的
（兩個落點都成立，而我只有「丟了 5 筆」這一個總和讀數）。
⇒ 那是**量不到**，⛔ 不是「兩個都是主因」。

⚠ 射程：本單量的是 `tavern-write` 這條路，⛔ 但成因在 `Submit`／`ServerExecutor`／`AgentCmdClient`，
**與 Cmd 種類無關** ⇒ 每一支走 Server 委派的 Cmd 都在射程內。

\## 三個落點

\### ① client 的 append 上鎖（`SCP_FileLock`，新檔）

`queue.json` 是「讀整檔 → 改 → 寫回整檔」而**多寫入端**（每顆 CLI／Unity Editor／執行器）。
`SCP_ServerCmdClient.Submit`（Unity 那條）與 `AgentCmdClient.Submit`／`RemoveCmd`（CLI 那條）都進鎖，
⚠ **載入也在鎖裡面** —— 拿著鎖去寫一份拿鎖之前讀的副本，鎖一點忙都幫不上。

⭐ 鎖用的是**開著的檔案握把**（`FileShare.None`），⛔ 不是標記檔：
標記檔要自己判「持有者死掉留下的幽靈鎖」，而那是一個新的、會誤判的讀數。
握把由 OS 在行程結束時收回 ⇒ 那一整族問題**不存在**。
📌 這是換框架不是加邏輯 —— 而我的已知盲點第一條正是「我的預設反應是加邏輯」，所以這一格我特別記一筆。

\### ② 執行器收尾**重讀磁碟**，只拿掉這一批碰過的 id

🩸 舊版是 `SaveQueue(批次開始時載入的那份副本)`。⚠ 那不是窄窗口的競態，是**整批時長那麼寬**的窗口。
⛔ 沒有在整批期間握著鎖（那會把 client 擋到逾時）—— 要的只是「寫回的那一瞬間依據磁碟現況」。

\### ③ 🔴 `AgentCmdWaitResult.Unknown = 7`

舊版「不在 queue ＋ 無判定檔」回 **Success**，理由是相容不寫判定檔的舊版執行端 ——
而同一個形狀也是「這筆 append 被寫回蓋掉」的樣子，**兩者處置相反**。
六處原本特判 `== Timeout` 的改讀 `IsIndeterminate()`，⚠ **而訊息文字跟著分**：
把 Unknown 印成「逾時」就是一個比事實大的名字（逾時聽起來只要再等就好）。
