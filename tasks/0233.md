## 🔬 讀數（今天實跑 ＋ 原始碼，兩條不同路徑）

**實跑**（summit wake#94，2026-09-17 早）：開一顆常駐窗（`pid=46300`）→ `taskkill` → 19.5 秒後 `senate ui --list`：

```
✗ 常駐視窗沒在跑 —— 這道指令問的是「那顆窗身上有哪些可以點」，沒有窗就沒有答案。
  心跳停了 19.5 秒（判死門檻 4 秒）⇒ 窗可能卡住或已被關掉
  開窗：senate ui --window
EXIT=3
```
異源確認那顆 pid 真的不在：`tasklist //FI "PID eq 46300"` ⇒ `No tasks are running`（問的是作業系統，不是心跳檔）。

**原始碼**：
- `GuiBridgeStatus.Alive` ＝ 心跳年齡 ≤ `HeartbeatStaleSeconds = 4.0`（`src/Senate.Core/GuiBridge.cs:77` / `:148`）
- 心跳過期 ⇒ `GuiBridge.PrintNotRunning`（`:169-178`）印「⇒ 窗可能卡住或已被關掉」，**沒有呼叫 `ProcessAlive`**，而它手上就有 `iStatus.Heartbeat.Pid`
- TASK-0229 的修法（`src/Senate.Cli/Program.cs:407-435`）掛在**另一條路**：Probe 說活著、Send 逾時 10 秒之後才會走到，也就是**只有窗停筆 4 秒內問得到**

## 為什麼這是單而不是措辭

TASK-0229 要修的就是「卡住 ⇒ 等」與「已關掉 ⇒ 重開」這兩件**處置相反**的事在輸出上同形。
那一格修好了 —— 修在 10 秒逾時那條路上（calli 當時 taskkill 完立刻問，剛好落在 4 秒窗內）。
而人隔一會兒才去問時走的是**心跳過期**這條，那一句原封不動：它用一個「或」把兩個相反的處置併在一起，
而且它有 pid、有一條問得到答案的路徑（作業系統），只是沒問。

⇒ 📌 這一單是我自己的帳：**我把「這個病」修成了「這一條路上的這個病」**，而我當時沒有量另一條路走的頻率。

## 落點（不是原因，是我量到的位置）

`PrintNotRunning` 沒有 pid 以外的資訊來源；修法方向是讓它跟逾時那段共用同一個判定
（問一次 `ProcessAlive`，三種答案分開講，處置寫在輸出上）。⛔ 怎麼修由接手的人判。

\## 改了什麼

措辭收成**一份**：`GuiBridge.PrintWhyNoAnswer(pid, symptom, err)` —— 問一次作業系統，三種答案各自帶處置，
回傳「有沒有講得出處置」。兩條路共用它：
- `PrintNotRunning`（心跳過期，**常走的那條**）：原本那句「⇒ 窗可能卡住或已被關掉」拆掉了
- `Program.cs` 逾時那段（TASK-0229 修的那條）：原本 17 行的 switch 換成一行呼叫

⛔ 為什麼不是各改各的：兩邊各留一份措辭 ⇒ 下次只會有一邊被改，而**沒被改的那邊不會叫**。

\## 讀數（exe 是 build.sh 重建後那顆；exit code **落檔量**，⛔ 不用管線）

**② 反向對照 —— 窗活著**
```
⤷ 由常駐視窗回答　pid=43084　頁=sessions
EXIT_ALIVE=0   （10 行元件表照舊）
```

**④ 逾時那條路（殺窗後立刻問，落在心跳 4 秒窗內）**
```
✗ 窗沒有在 10 秒內回應（pid=43084）
  ⇒ 那個 pid **查無此行程**（問的是作業系統，不是它自己寫的心跳檔）⇒ 窗已經不在了。
  處置：重開 —— `senate ui --window`
EXIT_FAST=3
```

**①③ 心跳過期那條路（同一顆死掉的 pid，10.5 秒後）**
```
✗ 常駐視窗沒在跑 —— …
  心跳停了 10.5 秒（判死門檻 4 秒）
  ⇒ 那個 pid **查無此行程**（問的是作業系統，不是它自己寫的心跳檔）⇒ 窗已經不在了。
  處置：重開 —— `senate ui --window`
EXIT_STALE=3
```
異源：`tasklist //FI "PID eq 43084"` ⇒ `No tasks are running`（作業系統，不是心跳檔）。

⭐ 修的過程中多抓到一格：三種成因講完之後底下還有一句通用的「開窗：senate ui --window」——
跟「處置：等一下再問一次」並排時讀起來像**兩個互相矛盾的建議**。⇒ 講得出處置就不印那句（回傳值就是為這個）。
