# TASK-0111 — 對外文案裡的 @<persona> 會連到真實第三方帳號 —— 對內沒送達、對外標錯人

> `bug` / `wrong` / `high` / `todo`　開單：summit　⚠ **尚無參與者**（沒有人在做這件事）

## 驗收標準

## 現象

我們在 Plurk 對外文案裡寫 `@<persona 名>`（`@summit` / `@basecamp` / `@calli`…），
以為那是在點名同事。**它不是。**

Plurk 的 @ 綁的是**帳號 nick**：我的 nick 是 `zeta_summit`、basecamp 的是 `cc_basecamp`。
⇒ `@summit` 對內**從來沒有送達過任何人**，而對外 Plurk 會把它 **linkify 成真實帳號連結**。

## 硬證據（從 Plurk 抓回來的已發布內容，不是我推的）

`plurk_summit__responses_358586412711248.json` 裡那則的 `content`（HTML）：

```html
<a href="https://www.plurk.com/summit" class="ex_link">summit</a> 我們差 20 秒押了同一個數字…
```

⇒ `content_raw` 是 `@summit`，而 Plurk 存回來的 HTML 是**指向 `plurk.com/summit` 的連結**。

## 為什麼這比「功能沒做」嚴重

- 它**不會叫**：`op=lint` 只算字數與署名，`@summit` 完全合法。
- 兩層都錯而方向相反：**對內沒送到**（同事收不到）＋**對外送錯人**（陌生人被公開標注）。
- 而「對內沒送到」讓我們**更常寫它** —— 因為沒有人回，看起來像對方沒空，不像沒收到。

## 建議修法（分兩段，前段是止血）

### ① 止血：`op=lint` 擋下文案裡的 `@<已知 persona 名>`
- 命中就**擋**（不是警告）：印出「`@summit` 會連到 `plurk.com/summit`（id 3905812，不是妳）」
  ＋ 給正確寫法（`@zeta_summit`）或建議改成非 @ 形式（`summit：`）。
- 判準表就是上面那張 —— **persona 名 → 真 nick** 的對照要落成資料，不是寫在 skill 裡讓人記。
- ⛔ 不要做「自動轉譯」：`@summit` → `@zeta_summit` 看起來很方便，
  但共用帳號（`hololive@myth` 一帳三人）**沒有一對一的 nick 可以轉**，
  轉譯會在那裡猜一個人出來。擋下來讓人自己寫，比替他猜對得多。

### ② 對內路由：`op=mentions` 讀取端支援 persona
見 TASK-0110 —— 讀取端是我們自己的，可以把 `@persona` 與**末行署名**當路由鍵。
⚠ 但那是**讀取端**的事，不能拿來當「所以可以繼續這樣寫」的理由：
**對外那條連結還是會連到陌生人。**

\## 〇、先講量到的，因為它推翻了我自己的顧慮

私噗探針 `358595023405481`（公開度＝本人，全部 @ 我自己的 nick，零第三方影響）。
Plurk 存回來的 `content`（HTML）逐項對照：

| 送出（raw） | 存回（HTML） | nick 終止 | payload 存活 |
|---|---|---|---|
| `@zeta_summit<aaa>` | `…zeta_summit</a>&lt;aaa&gt;` | ✅ | ✅ **被 HTML escape，畫面顯示 `<aaa>`** |
| `@zeta_summit（bbb）` | `…</a>（bbb）` | ✅ | ✅ |
| `@zeta_summit:ccc` | `…</a>:ccc` | ✅ | ✅ |
| `@zeta_summit#ddd` | `…</a>#ddd` | ✅ | ✅（**未被當 hashtag linkify**） |
| `@zeta_summit・eee` | `…</a>・eee` | ✅ | ✅ |

⇒ **五種都可行，尖括號不會被吃掉** —— 我先前「`<gura>` 可能被當未知標籤吞掉」的顧慮**不成立**，
在這裡撤回。分隔符的選擇因此不是存活問題，是人機介面問題。

📌 而有一項是**量出來的淘汰**：半角 `(xxx)` 撞現有 lint 守衛「疑似編輯註記留在文案裡」

\## 一、分隔符提案：`→`

```
@hololive_myth→gura
```

| 判準 | `→` | `<gura>` | `#gura` | `:gura` | `・gura` |
|---|---|---|---|---|---|
| 技術存活（已量） | ✅ | ✅ | ✅ | ✅ | ✅ |
| 撞現有 lint | 無 | 無 | 無 | 無 | 無 |
| 對**外人**讀起來是什麼 | 「**給 gura**」語意直接 | 像模板殘留／佔位符 | 像**話題標籤**（河道上 `#原耽` 那種） | 像「該帳號說：gura」——**Plurk 自己就是這樣渲染 bot 回應的**（`@klf101: 還差一點啊`） | 像日式並列名（myth・gura），語意是「和」不是「給」 |
| 機器解析 | 單一字元、不與內文衝突 | 需配對 | `#` 之後可能有真 hashtag 相鄰 | `:` 在中文文案裡太常見 | 少見但可 |
| 打得出來 | 需輸入法 | ASCII | ASCII | ASCII | 需輸入法 |

⇒ **推薦 `→`**，唯一的代價是它不是 ASCII（而我們的文案本來就滿是全形符號與 emoji，這格成本很低）。
⛔ **`:gura` 明確反對** —— Plurk 的 bot 回應本身就用 `@nick: 內容` 這個形狀，撞得最兇。
若要 ASCII，第二順位是 **`<gura>`**（你原提案）——它量過可行，只是對外人像模板殘留。

\## 二、發文端（outbound）：`@persona` → 真 nick ＋ 標記

```
@gura      →  @hololive_myth→gura     （共用帳號：一帳三人，標記必要）
@summit    →  @zeta_summit            （1:1 帳號：nick 已唯一，**不加標記**）
```

**為什麼 1:1 不加標記**：我們的文案是公開的、給人看的。
`@zeta_summit→summit` 對外人是純噪音，而它換不到任何路由能力（nick 已經指到唯一的人）。
⇒ **只有「該帳號承載 >1 persona」時才加標記。**

\### 三條硬規矩

1. **對照表是資料不是文件** —— `persona → (account, nick, 是否共用)` 落成一份檔，
   不要寫在 skill 裡讓人記。skill 會漂，而漂了不會叫。
2. **查不到 persona 時要大聲失敗，不准靜默放行** ——
   🩸 現況就是靜默放行：`@Sirius` 查無對應 nick，而它照樣發了出去（快取裡有）。
   ⇒ lint 命中未知 persona 名 ⇒ **擋**，並印「這個名字沒有對應帳號，它會連到 `plurk.com/<那串>`」。
3. ⛔ **不做「猜一個」的轉換** —— 共用帳號沒有一對一的 nick 可轉；
   任何自動挑人都是替使用者決定了收件人。查不到就擋，讓人自己寫。

\## 三、讀取端（inbound）：四層優先序，每層都寫明它的代價

| 層 | 判準 | 為什麼這樣排 |
|---|---|---|
| **1** | 內文有 `@<nick>→<persona>`（我們自己的格式） | 最準：發的人明確指定了 |
| **2** | ⭐ **他回的是「哪一則貼文」，就路由給那則貼文的末行署名** | **零外部依賴** —— 外人不必學我們的慣例。共用帳號在回應裡 @ 帳號時，這一層就夠了 |
| **3** | 內文出現 persona 名但沒有標記 | 標**疑似**，不標「已 @」。🩸 我 09-02 就因為「憑訊息在畫面上的位置認人」把 calli 做的事記成 kiara 的 |
| **4** | 只 @ 了帳號 nick、其他都沒有 | ⛔ **不替他們挑人**。印「這則點名的是帳號不是人」並列出該帳號所有 persona，由人決定誰回 |

📌 第 2 層是 Tim 今天補的那句「末行署名當路由鍵也 ok」的落點，而它比我原本想的更強：
**署名是我們早就在強制產出的東西**（共用帳號末行必署名），
所以這一層**今天就有資料可用，不需要任何人改行為**。

⚠ 第 2 層的邊界要寫進回傳檔：如果那則貼文**沒有署名**（1:1 帳號不強制），
就退到第 4 層，而不是拿帳號主人當預設 persona。
