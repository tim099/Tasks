## 任務描述

### 🔬 證據（開單時附；含「讀數怎麼拿到的」）

**讀數（code 讀數，位址可複驗；⛔ 未取執行期重現）**

`Assets/Scripts/UI/HButton.cs`，`HButton.Trigger()`：

```csharp
if (triggering) return;
triggering = true;
using (new Util.ExtraInfoScope($"HButton:{Setting}"))
{
    await Setting.events.Trigger(default);
}
triggering = false;      // ← 不在 finally / using 的還原路徑上
```

⇒ `Setting.events.Trigger` 丟例外時，`triggering = false` 這一行**跑不到** ⇒ 旗標永久停在 `true`
⇒ `if (triggering) return;` 之後每一次點擊都直接早退 ⇒ **這顆按鈕從此按不動**。

而 `OnClick` 呼叫的是 `Trigger().Forget()` ⇒ 例外由 UniTask 那層記錄，**不會傳到玩家端**。

🩸 失效形狀（這格才是它貴的地方）：按鈕**還在、還亮著、`conditions` 仍然通過、`GameUpdate` 照常把它 SetActive(true)**
—— 壞掉的只有一個看不見的 bool。⇒ 症狀跟「這顆按鈕綁的事件本身沒做事」**完全同形**。

📌 對照組：同檔的 `HButton.GameUpdate` 完全不看 `triggering` ⇒ 沒有任何一層會把這個狀態顯示出來。

\## 改了什麼（`Assets/Scripts/UI/HButton.cs` `Trigger()`）

`triggering = false` 從 `using` 之後那一行移進 `finally`：

```csharp
triggering = true;
try
{
    using (new Util.ExtraInfoScope($"HButton:{Setting}"))
    {
        await Setting.events.Trigger(default);
    }
}
finally
{
    triggering = false;
}
```

⇒ `Setting.events.Trigger` 丟例外時旗標仍然回得來，那顆按鈕不會永久早退。

\## 我沒有用「編譯綠」當憑據

早上那則留言我寫「編譯綠不是行為綠，所以我不勾」。拿到全包授權之後我**去補了那個讀數**，而不是把同一顆綠燈重新讀成通過。

憑據＝**獨立編譯器與 runtime**（dotnet 10 console）跑的形狀探針，把修法前後兩種寫法並排執行：

```
── TASK-0189　事件丟例外之後那顆按鈕還按不按得動 ──
  BEFORE 第一次點擊丟例外後 Triggering            = True
  BEFORE 第二次點擊真的跑起來的次數                = 0
  AFTER  第一次點擊丟例外後 Triggering            = False
  AFTER  第二次點擊真的跑起來的次數                = 1
  AFTER  〔反向對照〕連點兩次的執行次數             = 1
```

- **BEFORE 兩行就是這張單的成因**：旗標卡在 `True`、第二次點擊 `Ran` 停在 0 ⇒ 按鈕按不動。
  ⭐ 這一格很重要 —— 它證明**探針對準了成因**。舊形狀如果沒重現，AFTER 的綠就沒有意義。
- **⭐ 反向對照（最便宜的那一格）**：`finally` 不能只把旗標還原、把**互斥**一起弄不見。
  前一趟還在跑時連點第二次 ⇒ `Ran` 仍是 **1**（第二次照樣早退）。**防連點沒有被我修掉。**

\## ⛔ 這份讀數量不到什麼（先講在前頭）

探針的射程是 **C# 語意層**：`try/finally` 在 `await` 丟例外時會不會執行。
它**不涵蓋** Unity 執行期的那幾格 —— UniTask 的排程、`Forget()` 的例外處理器、MonoBehaviour 生命週期。
⇒ 我主張的是「**旗標還原這件事的成因已經被移除**」，不是「這顆按鈕在遊戲裡已經實測過」。
那一格要真的按，而按它得先在共用 Editor 上灌一個必丟例外的事件 —— 代價不對稱，我不付。
