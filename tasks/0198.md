### 🔬 證據（開單時附；含「讀數怎麼拿到的」）

## 症狀

TASK-0195 修好了「查無被算成用完」（收工印「用 10 張、全數用畢」而實際 0 張），
而修法的 fallback 在**今晚同一小時內對三個人生效**，印的是：

> 🎟 限時券用量：**帳本查無本場批次**（不猜 —— 見 TASK-0195）

⇒ 那句話**誠實但沒有用**：問「我這場用了幾張」的人，得到的是「不知道」。

## 🔬 讀數（2026-09-10 23:20 前後，同一批自由時間收工公告）

| persona | 收工公告印的 | 實際 |
|---|---|---|
| kiara | 帳本查無本場批次 | 未知（她 7 輪活動） |
| gura | 帳本查無本場批次 | 未知（3 輪） |
| basecamp | 帳本查無本場批次 | **十張全用了**（她自己在噗浪說的） |
| meadow | 用 1/10 張、9 張到期作廢 ✅ | 對得上 |
| summit | 用 0/10 張、10 張到期作廢 ✅ | 對得上（我一顆沒放） |

⇒ 分界看起來是**批次還在不在**：沒用完的批次還躺在帳本上 ⇒ 查得到；
用完（remain=0）或已被清理的 ⇒ `TryGetUsageByRef` 回 false ⇒ 印「查無」。

## 🩸 而它是一次不等價的交換（這是本單的重點）

修法**前**那條 `發放量 − 未過期餘額` 在「**用完**」這個 case **剛好會印對**（10 − 0 = 10）。
修法**後**同一個 case 變成「無法判定」。
⇒ **我把一個偶然對的答案，換成了一個誠實但沒用的答案。**
⛔ 誠實不是這一格的目標，**能回答「用了幾張」才是**；而誠實只是不准用猜的去補。

## ⛔ 射程

- 只補 `TryGetUsageByRef` 查無時的**回退讀法**：`history` 裡有該 ref 的 `grant`（發放量）
  與該 batch 的 `expire`（作廢量）⇒ **用量 = grant − expire − remain**，三個值都已經在檔裡。
- ⛔ 不改 `overlapping`/計費/`--pay auto` 優先序；⛔ 不改既有欄位語意。
- ⚠ 未量：history 被裁剪（若有上界）時這條回退也會失效 —— 本單第一步先確認那份 history 有沒有上界。

## 結單說明

QA 驗收通過：在 Template 實跑 grant 10/consume 10 驗證 exhaust 留痕與 history 結算，op=usage 與 Cmd_FreeTime 回退讀法均正確回傳 used=10/10、forfeited=0，5/5 驗收標準全數勾銷。

\## 🔬 而本單開單時寫的補法**算不出來** —— 那是一個沒讀 schema 就開的處方

原字面：「查無時改讀 history 的 grant 與 expire 差額（兩者都在檔裡）」。實際 schema：

- `expire` 那一列是**加總的**（多批同時過期併成一筆），而它的 `ref` 欄填的是人看的字串 **「到期作廢」** —— 而 `ref` 在別的列一律是**批次的 ref**。⇒ glossary `借位`：欄位合法、值合法，而它回答的是另一個問題。
- `consume` 的 `ref` 是**每一次放點**的 ref（`a9eb3d` 這種），不是 session 的 ref。
- 花完的批次**一個字都不留** ⇒ 它跟「這一批從來不存在」同形。

⇒ 所以修法不在讀取端，在**寫入端**（@apex-one 那句：判準寫在畫面上不算寫，要寫在寫入端）。

\## ✅ 落地（`UCL_Core` 兩檔，Unity Errors 0 / stale_sources 0 / 耗時 2.42s ⇒ 不是 0.25s 那種假 clean）

1. `UCL_CanvasVoucherLedger.MutateLedger` 清理留痕改成**逐批可歸戶**：過期 ⇒ 一批一筆 `expire`（`ref`＝批次 ref、`batch`＝uuid，人看的字串移到 `source`）；花完 ⇒ 新增一筆 `exhaust`。
   ⛔ 為什麼花完也要留痕：否則就得從**缺席**推用量（「grant 有、batches 沒有 ⇒ 一定是用完了」）—— 而缺席的另一個成因是檔被重建／別棵 DataRoot。「未量」與「零」同形，這條我今天不想再犯第六次。
2. 新增 `TryGetUsageFromHistoryByRef`：`grant` − `expire`（有 `exhaust` ⇒ forfeited 0）。**回 false 時三個值歸零** —— 見下面那格血證。
3. `Cmd_FreeTime` 收工：batches → history → 查無，三態。而 **history 那一條的公告字串明寫「自券帳 history 結算」** ⇒ ⛔ 兩條路的答案不准同形，否則「讀得到批次」與「批次已結清」印出一模一樣的字，就是 0195 那族換個地方發作。
4. `Cmd_CanvasVoucher` 新增唯讀 `op=usage`（persona + ref → granted / used / forfeited ＋**讀數源**）。
   理由是判準④：這個問題原本只有一個消費端（收工公告），要驗它就只能用被驗的那支本身當尺（同源）。現在有第二個呼叫者。

\## 🩸 而我造的那道新門，第一版就把原病遞了出去

`op=usage` 第一版在 `found=0` 的時候仍然印 `granted=10`（因為 history 那支先累加 grant 才判定失敗）。
⇒ 一個 `granted=10` 擺在 `found=0` 旁邊，就是把「**10 − 0**」這個減法交給下一個呼叫端 —— **那正是 TASK-0195 的原始公式**。
📌 抓到它的是我把五個 case 的機讀輸出列成一張表、看到那一格數字**不該在那裡**；不是我更仔細。
⇒ 修法是讓它拿不到那個數字（庫層回 false 時歸零 ＋ Cmd 層查無時**不發**那三欄）—— 欄位缺席會讓機讀端炸，帶一個不可用的數字會讓它靜默算錯。
